# Phase 1 — Accounts: Low-Level Design

**Branch:** `feature/auth`
**Covers:** FR-P1, FR-P2, FR-D1, FR-D2, FR-W1, FR-S1, FR-S2 · NFR-6, NFR-7, NFR-8, NFR-10, NFR-11, NFR-12, NFR-22, NFR-23, NFR-35, NFR-43

This phase lets people create an account, sign in and out, and see who they are. Every user gets a TeslaPay wallet, and a driver registers their Tesla when signing up. Nothing here books a ride yet.

---

## 1. Scope

**In**

- Sign up as a passenger or a driver. A driver registers one Tesla at the same time.
- Sign in and sign out with a 24-hour session cookie.
- `GET /me`: the signed-in user, their wallet balance, and the driver's Tesla.
- Role checks that later phases reuse on passenger and driver routes.
- The seed gives every cast member a wallet, and gives Jashim the Tesla "Bullet".

**Left for later phases**

| What | Phase |
|---|---|
| Driver online/offline and location columns on the vehicle | 2 |
| Passenger's current ride in `/me` | 2 |
| `occupied_seats`, `version` and the capacity CHECK on seats taken | 4 |
| Wallet routes, top-ups, the ledger, the negative-balance rule | 6 |

## 2. Tables

Two migrations, generated by drizzle-kit and reviewed by hand.

### `wallets` (FR-W1)

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | `gen_random_uuid()` |
| `user_id` | `uuid` NOT NULL UNIQUE → `users.id` | One wallet per user |
| `balance` | `numeric(10,2)` NOT NULL DEFAULT `0` | Sent over the API as a string, e.g. `"0.00"` |
| `updated_at` | `timestamptz` NOT NULL DEFAULT `now()` | |

- Sign-up creates the wallet in the same transaction as the user.
- The migration backfills a wallet for every user that already exists. Databases created in phase 0 already hold users, and "every user has a wallet" must hold for them too.
- Balances stay at `0.00` in this phase. The ledger (`wallet_transactions`) arrives in phase 6. A non-zero balance with no ledger entry behind it would break NFR-39, so the seed doesn't top anyone up yet.

### `vehicles` (FR-D1)

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | |
| `driver_id` | `uuid` NOT NULL UNIQUE → `users.id` | Exactly one Tesla per driver |
| `name` | `text` NOT NULL | e.g. "Bullet" |
| `capacity` | `integer` NOT NULL | `CHECK (capacity BETWEEN 1 AND 6)` |
| `created_at`, `updated_at` | `timestamptz` NOT NULL DEFAULT `now()` | |

- **Assumption:** at most 6 passenger seats, since the largest Tesla (Model X, 7 seats) carries 6 passengers besides the driver.
- The database doesn't check that `driver_id` points at a driver. The sign-up service guarantees it, because it creates the vehicle only for the driver role, in the same transaction as the user.

## 3. Sessions

The spec says a signed cookie is enough (Core Entities §3), so there is no sessions table.

| Item | Decision |
|---|---|
| Token | JWT, HS256, signed with `jose`. Claims: `sub` = user id, `role`, `iat`, `exp` = 24 h. |
| Secret | `SESSION_SECRET` env var, at least 32 characters (NFR-11). The API refuses to start without it. |
| Cookie | `tp_session`: `HttpOnly`, `SameSite=Lax`, `Path=/`, `Max-Age=86400` (NFR-6) |
| `Secure` flag | `COOKIE_SECURE` env var. It defaults to on when `NODE_ENV=production`. Docker Compose turns it off because it serves plain `http://localhost`. Deployed hosts keep it on (NFR-5). |
| Expiry | Fixed 24 h from sign-in. It doesn't slide. |
| Role in the token | Roles never change, so role checks need no database read (NFR-1). |

**Cross-site requests.** `SameSite=Lax` stops the browser sending the cookie on cross-site POSTs, and the API only reads JSON bodies. Together these cover CSRF for this app.

**Sign-out** clears the cookie. Tokens are stateless, so a token copied before sign-out keeps working until it expires. This is listed under known limitations.

## 4. Routes

All routes are under `/api/v1`. Bodies are validated with Zod. Invalid input returns `400 VALIDATION_ERROR` with `details: [{ path, message }]` (NFR-10).

### `POST /auth/signup`

```jsonc
// passenger
{ "role": "passenger", "name": "Nusrat", "email": "nusrat@example.com",
  "password": "********", "gender": "female" }

// driver
{ "role": "driver", "name": "Jashim", "email": "jashim@example.com",
  "password": "********", "gender": "male",
  "vehicle": { "name": "Bullet", "capacity": 3 } }
```

| Field | Rule |
|---|---|
| `role` | `passenger` or `driver`. It selects which shape the body must have. |
| `name` | Trimmed, 1–80 characters |
| `email` | A valid email. It is trimmed and lowercased before storing, so `Nusrat@X.com` and `nusrat@x.com` are the same account. |
| `password` | 8–72 bytes. bcrypt ignores anything past 72 bytes, so longer passwords are refused rather than silently cut. |
| `gender` | `female` or `male`. Required (FR-P1), because the same-gender pool needs it. |
| `vehicle` | Drivers only, and required for them. `name` is trimmed, 1–40 characters. `capacity` is a whole number from 1 to 6. A passenger sending `vehicle` is an error. |

- One transaction inserts the user, the wallet and, for a driver, the vehicle. Either all three are created or none are (NFR-14).
- The password is hashed with bcrypt (cost 10) before the transaction opens (NFR-7).
- A taken email returns `409 EMAIL_TAKEN`. The code relies on the unique constraint and catches its violation instead of checking first. That way, two sign-ups racing for one email can't both succeed.
- **201** with the `/me` body, and the session cookie is set, so a new user is signed in straight away.

### `POST /auth/login`

`{ "email": "...", "password": "..." }` → **200** with the `/me` body and the session cookie.

- An unknown email and a wrong password both return the same `401 INVALID_CREDENTIALS`. For an unknown email the code still compares the password against a dummy hash, so response times don't reveal which emails are registered.

### `POST /auth/logout`

Clears the cookie → **204**. It works with or without a session, so pressing it twice is safe (NFR-37).

### `GET /me`

Requires a session.

```json
{
  "user": {
    "id": "…", "name": "Jashim", "email": "jashim@teslapool.test",
    "gender": "male", "role": "driver", "createdAt": "2026-09-24T02:41:00.000Z"
  },
  "wallet": { "balance": "0.00" },
  "vehicle": { "id": "…", "name": "Bullet", "capacity": 3 }
}
```

- `vehicle` is `null` for passengers.
- The password hash is never selected from the database.
- If a valid token names a user that no longer exists, the response is `401 UNAUTHENTICATED`.

### Error codes added in this phase

| Status | Code | When |
|---|---|---|
| 409 | `EMAIL_TAKEN` | Sign-up with an email that already has an account |
| 401 | `INVALID_CREDENTIALS` | Sign-in with a wrong email or password |

`UNAUTHENTICATED` (401) and `WRONG_ROLE` (403) already exist and are used from this phase on.

## 5. Access checks (NFR-8)

| Middleware | Rule | Failure |
|---|---|---|
| `requireAuth` | Verifies the cookie's signature and expiry, then attaches `{ userId, role }` to the request | Missing, tampered or expired token → `401 UNAUTHENTICATED` |
| `requireRole(role)` | Runs after `requireAuth` | Another role → `403 WRONG_ROLE` |

No route in this phase is limited to one role. From phase 2 on, `/driver/*` routes use `requireRole('driver')` and passenger ride routes use `requireRole('passenger')`. Checking that a resource belongs to the user (404 when it doesn't) happens in each service, from phase 2.

## 6. Code layout (NFR-26)

```
apps/api/src/
  auth/password.ts            bcrypt hash and verify, shared with the seed
  auth/session.ts             sign and verify the JWT; cookie name and options
  http/middleware/auth.ts     requireAuth, requireRole
  services/accounts.ts        sign-up, sign-in and /me; owns the transactions
  routes/v1/auth.ts           /auth/* handlers: validate, call the service, set the cookie
  routes/v1/me.ts             /me handler
  db/schema/wallets.ts
  db/schema/vehicles.ts
```

Routes stay thin. The service takes the database as a parameter, so the tests exercise the same code the server runs.

## 7. Seed (FR-S1, FR-S2, NFR-31)

The seed runs in one transaction and is safe to repeat:

1. It inserts the four cast members if their emails are missing (unchanged from phase 0).
2. It inserts a wallet for each cast member who has none.
3. It inserts **Bullet**, capacity 3, for Jashim if he has no vehicle.

Running it again changes nothing. The demo password stays `TeslaPool#2026`, as documented in the README.

## 8. Frontend

| Screen | Contents |
|---|---|
| `/` | App name and tagline, with Sign in and Create account. A signed-in user goes straight to their home. |
| `/signup` | Name, email, password, gender, and a Passenger / Driver switch. Choosing Driver shows the Tesla's name and seat count. |
| `/login` | Email and password |
| `/passenger` | Greeting, wallet balance and a Sign out button. Rides arrive in phase 2. |
| `/driver` | Greeting, wallet balance, the Tesla's name and seats, and a Sign out button |

- The browser calls the API through the Next.js proxy at `/api/v1/*`, so the cookie is first-party.
- `src/proxy.ts` makes a quick check that the session cookie exists, only to avoid flashing the wrong page. The real check is `/me`: a 401 sends the user to `/login`, and a user of the wrong role is sent to their own home.
- Field errors come from the error envelope's `details[].path`. `EMAIL_TAKEN` is shown under the email field.
- The submit button is disabled while a request is running, so a double tap sends one request (NFR-37).
- Every screen shows a loading state, and errors in plain words (NFR-22). Money is shown as `৳ 0.00`, formatted from the API's string without floating-point maths (NFR-23).

## 9. Tests

| Area | Cases |
|---|---|
| Sign-up | A passenger gets a wallet at `"0.00"` and a hashed password. A driver gets a vehicle. The cookie is `HttpOnly`, `SameSite=Lax` and `Max-Age=86400`. A driver without a vehicle, a passenger with one, a missing gender, and capacity 0 or 7 are all rejected with 400. |
| Duplicate email | A second sign-up whose email differs only in case gets 409. Ten concurrent sign-ups with one email produce exactly one account. |
| Sign-in | Correct details sign the user in. A wrong password and an unknown email get identical 401 responses. |
| Sign-out | 204, and the cookie is cleared |
| Sessions | No cookie, a tampered token, a token signed with another secret, and an expired token each get 401 from `/me`. `/me` never includes the password hash. |
| Roles | A passenger on a driver-only route gets 403. No session gets 401. |
| Seed | Four wallets and one Bullet with capacity 3, unchanged after a second run |
