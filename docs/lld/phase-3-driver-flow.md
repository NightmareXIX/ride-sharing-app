# Phase 3 — Single ride lifecycle: Low-Level Design

**Branch:** `feature/driver-flow`
**Covers:** FR-P5, FR-P7 (cancel after acceptance), FR-P8, FR-P9, FR-P11 (in part), FR-D3, FR-D5, FR-D6, FR-D8, FR-D10, FR-D12, FR-D14, FR-R4, FR-R6, FR-R7, FR-R8, FR-R9, FR-R11, FR-F4, FR-F5, FR-F6, FR-W5 (in part), FR-C2, FR-C4, FR-C5 · NFR-1, NFR-3, NFR-8, NFR-9, NFR-14, NFR-22, NFR-27, NFR-37, NFR-38, NFR-40, NFR-41, NFR-44

This phase lets an online driver see ride requests near their Tesla and accept one. They then mark arrival, start the trip and complete it, and the final fare is recorded for the passenger to pay in cash. Before pickup, the driver can cancel, and the request goes back to other drivers. The passenger follows each step on their screen and can cancel until the trip starts. A Tesla carries one booking at a time in this phase. Pooling comes in phase 5.

---

## 1. Scope

**In**

- An idle online driver sees open requests whose pickup is near their Tesla.
- The driver accepts one. The booking joins a new pool for the Tesla.
- The driver marks arrival, starts the trip and completes it, one step at a time.
- On completion, the final fare is calculated and stored with its full breakdown.
- The driver cancels before pickup, and the request returns to `REQUESTED` for any driver.
- The passenger cancels after acceptance, until the trip starts. The history records whether the cancel was inside the 3-minute free window.
- A driver with a passenger can't go offline or move their Tesla.
- The passenger sees their driver, the Tesla, each step and, at the end, the fare breakdown.

**Left for later phases**

| What | Phase |
|---|---|
| `occupied_seats`, the vehicle `version`, the seat CHECK, `POOL_CHANGED`, and the repeated single-claim and last-seat stress tests | 4 |
| More than one booking per Tesla, route stops and odometer readings, the matching rule (FR-L3), shared km, `OUT_OF_STOP_ORDER`, and the 3-requests-per-refresh route check (NFR-3) | 5 |
| The wallet ledger, TeslaPay payment and driver credit, cash-earning entries, the 30 tk late-cancel fine, no-show (`NO_SHOW_TOO_EARLY`), and driver penalty records | 6 |
| What Solo and Same-gender do to matching (FR-R10) | 7 |
| `GET /bookings`, `/driver/pools*`, `/driver/earnings` | 8 |

**One booking per Tesla.** The development plan calls this phase the *single* ride lifecycle. A driver sees requests only while idle, and accepting needs an idle Tesla. Phase 5 replaces the idle rule with the matching rule. Everything else built here (pools, the history's `pool_id`, the fare record) already has the shape pooling needs.

**Late cancels are recorded but not fined yet.** A passenger cancel more than 3 minutes after acceptance is allowed and stored with reason `late_cancel`, measured by the database clock (FR-R9, NFR-38). The 30 tk fine needs the wallet ledger, so phase 6 adds it. Until then, a late cancel is free.

**Settlement is cash only.** Completing a ride stores the fare. For a Cash booking, the passenger pays the driver in person (FR-W5). The cash-earning ledger entry arrives with the ledger in phase 6. A TeslaPay booking can't be created before phase 6, since every wallet is at `0.00` and FR-W3 refuses it.

**The "stop searching" option** (FR §13, deferred to the LLD). When a driver cancels, the passenger's request goes back to `REQUESTED`. The passenger can already cancel a `REQUESTED` booking for free, and their screen says why they're waiting again. That is the stop-searching option. No new route is needed.

## 2. Tables

Three migrations, generated by drizzle-kit and reviewed by hand. The trigger in `0008` is hand-written, as in `0005`.

### `pools` (Core Entities: Pool)

New enum `pool_status`: `active`, `finished`.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | |
| `vehicle_id` | `uuid` NOT NULL → `vehicles.id` | |
| `status` | `pool_status` NOT NULL DEFAULT `'active'` | |
| `created_at` | `timestamptz` NOT NULL DEFAULT `now()` | |
| `finished_at` | `timestamptz` NULL | |

- `CHECK ((status = 'finished') = (finished_at IS NOT NULL))`
- **One active pool per Tesla:** `CREATE UNIQUE INDEX pools_one_active_per_vehicle ON pools (vehicle_id) WHERE status = 'active'`. It is the database backstop for "one booking at a time" in this phase. It stays true in phase 5, where one active pool holds several bookings.

A pool is created by the first accept on an idle Tesla. It is `finished` once none of its bookings are active: every booking is `COMPLETED` or `CANCELLED`, or has been handed back by a driver cancel (FR-R7).

### `bookings` gains the lifecycle

| Column | Type | Notes |
|---|---|---|
| `pool_id` | `uuid` NULL → `pools.id` | Indexed. The pool the booking belongs to now (FR-R6). |
| `accepted_at` | `timestamptz` NULL | Starts the 3-minute free-cancel window |
| `arrived_at` | `timestamptz` NULL | Starts the 5-minute no-show wait (phase 6) |
| `started_at` | `timestamptz` NULL | |
| `completed_at` | `timestamptz` NULL | |

Every time is set with `now()`, the database clock (NFR-38).

CHECK constraints make the columns agree with the status:

| Constraint | Rule |
|---|---|
| `bookings_pool_accepted` | `(pool_id IS NULL) = (accepted_at IS NULL)` |
| `bookings_requested_unassigned` | `status <> 'REQUESTED' OR pool_id IS NULL` |
| `bookings_assigned_has_pool` | `status NOT IN ('ACCEPTED', 'DRIVER_ARRIVED', 'STARTED', 'COMPLETED') OR pool_id IS NOT NULL` |
| `bookings_arrived_at` | `status NOT IN ('DRIVER_ARRIVED', 'STARTED', 'COMPLETED') OR arrived_at IS NOT NULL`, and `arrived_at IS NULL OR accepted_at IS NOT NULL` |
| `bookings_started_at` | `(started_at IS NOT NULL) = (status IN ('STARTED', 'COMPLETED'))` |
| `bookings_completed_at` | `(completed_at IS NOT NULL) = (status = 'COMPLETED')` |

- A **driver cancel** clears `pool_id`, `accepted_at` and `arrived_at`, because the request is waiting again. The history row keeps the pool it left (below). `requested_at` doesn't change, so a re-surfaced request stays near the front of the queue.
- A **passenger cancel** after acceptance keeps `pool_id`, so the driver's trip history in phase 8 still shows it.

### `booking_status_history` gains `pool_id`

| Column | Type | Notes |
|---|---|---|
| `pool_id` | `uuid` NULL → `pools.id` | The pool the booking was in when it changed. For a driver cancel, this is the pool it left. |

Reasons used from this phase on:

| Reason | Change |
|---|---|
| `requested` | NULL → REQUESTED |
| `passenger_cancel` | → CANCELLED by the passenger, free |
| `late_cancel` | → CANCELLED by the passenger, more than 3 minutes after acceptance |
| `accepted` | REQUESTED → ACCEPTED |
| `driver_arrived` | ACCEPTED → DRIVER_ARRIVED |
| `started` | DRIVER_ARRIVED → STARTED |

| `driver_cancel` | ACCEPTED or DRIVER_ARRIVED → REQUESTED |

### `fares` (Core Entities: Fare)

One row per completed booking, written in the same transaction as the completion.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | |
| `booking_id` | `uuid` NOT NULL UNIQUE → `bookings.id` | |
| `pickup_odometer_km`, `dropoff_odometer_km` | `numeric(8,3)` NOT NULL | |
| `actual_km` | `numeric(7,3)` NOT NULL | `dropoff − pickup` |
| `shared_km` | `numeric(7,3)` NOT NULL | |
| `direct_km` | `numeric(7,3)` NOT NULL | Copied from the booking |
| `seats` | `integer` NOT NULL | |
| `seat_multiplier` | `numeric(4,2)` NOT NULL | |
| `ride_option` | `ride_option` NOT NULL | |
| `option_multiplier` | `numeric(4,2)` NOT NULL | |
| `estimated_fare`, `computed_fare`, `final_fare` | `numeric(10,2)` NOT NULL | |

| `created_at` | `timestamptz` NOT NULL DEFAULT `now()` | |

- `CHECK (final_fare <= estimated_fare)` (FR-P4) and `CHECK (shared_km <= actual_km)`.
- **Never changed (NFR-41).** The `reject_update_delete()` trigger from `0005` is attached `BEFORE UPDATE OR DELETE`.
- **Odometer in this phase.** A single ride's route is its pickup followed by its destination. So the pickup reading is `0.000`, the drop-off reading is `direct_km`, `actual_km = direct_km` and `shared_km = 0`, which makes the computed fare equal the estimate. Phase 5 takes the readings from the pool's route stops instead. The table and the formula stay the same.

## 3. Routes

All routes are under `/api/v1`, and bodies and params are validated with Zod. A booking id that isn't a UUID is `404 NOT_FOUND`, as in phase 2.

### Driver: finding and accepting rides

Both routes use `requireAuth` and `requireRole('driver')`.

#### `GET /driver/requests`

Polled every 4 seconds while the driver is online and idle (NFR-3).

| Driver's situation | Requests shown |
|---|---|
| Offline | None |
| Has an active pool | None, until phase 5 |
| Online and idle | `REQUESTED` bookings that fit the Tesla (`seats ≤ capacity`) with a pickup within the search radius of the Tesla |

- The radius (default 2 km, FR-D6) is measured in a **straight line** from the Tesla's location. No map request is made, so the list is a plain database read (NFR-1). A bounding box in SQL narrows the rows, and `haversineKm` decides.
- Oldest `requested_at` first, at most 20.
- A driver sees the pickup and destination of requests they may accept (NFR-9). The passenger's name appears only once the driver has accepted.

```json
{
  "requests": [
    {
      "id": "…",
      "pickup": { "lat": 23.7937, "lng": 90.4066, "label": "Banani Road 11" },
      "destination": { "lat": 23.7781, "lng": 90.4050, "label": "Mohakhali" },
      "seats": 1, "rideOption": "pool", "paymentMethod": "cash",
      "directKm": "5.000", "estimatedFare": "130.00",
      "requestedAt": "2026-09-25T02:41:00.000Z",
      "pickupDistanceKm": "0.412"
    }
  ]
}
```

#### `POST /driver/requests/:bookingId/accept`

The driver picks the request; nothing is auto-assigned (FR-D8). Everything is checked again, since the list may be up to 4 seconds old. One transaction, locking the vehicle before the booking, which is the lock order FR-C7 sets:

1. Lock the driver's Tesla (`SELECT … FOR UPDATE`). Offline → `422 DRIVER_OFFLINE`.
2. Lock the booking. If it is already in this Tesla's active pool, the accept is a repeat. Return **200** with the current pool and change nothing (FR-C5, NFR-37).
3. The Tesla already has an active pool → `422 NO_LONGER_MATCHES`.
4. `seats > capacity` → `409 SEATS_UNAVAILABLE`. The pickup is now outside the radius (the driver moved, or the request came from an old list) → `422 NO_LONGER_MATCHES`.
5. Insert the pool, then `transitionBooking` REQUESTED → ACCEPTED, setting `pool_id` and `accepted_at = now()`, with reason `accepted`.
6. If the booking wasn't `REQUESTED`:

| Found | Response |
|---|---|
| Not there | `404 NOT_FOUND` |
| Accepted by another driver | `409 ALREADY_CLAIMED` (FR-R4) |
| Cancelled by the passenger | `409 INVALID_TRANSITION`: "This request was cancelled." |

The conditional `UPDATE … WHERE status = 'REQUESTED'` inside `transitionBooking` means only one driver can claim a request (FR-C2). The vehicle lock stops one driver accepting two requests at once, and `pools_one_active_per_vehicle` backs it up. Phase 4 adds the repeated concurrency tests for both.

The response is the driver's trip, as `GET /driver/pool` returns it.

### Driver: during the trip

All use `requireAuth` and `requireRole('driver')`. A driver can act only on bookings in their own Tesla's active pool. Any other booking is `404 NOT_FOUND` (NFR-8).

#### `GET /driver/pool`

Polled every 4 seconds while a trip is active. `{ "pool": null }` when the driver has none. The driver sees every passenger in the pool, their seats and their status (FR-D14):

```json
{
  "pool": {
    "id": "…", "createdAt": "…",
    "bookings": [
      {
        "id": "…", "passenger": { "name": "Nusrat" }, "status": "ACCEPTED",
        "pickup": { … }, "destination": { … },
        "seats": 1, "rideOption": "pool", "paymentMethod": "cash",
        "directKm": "5.000", "estimatedFare": "130.00",
        "acceptedAt": "…", "arrivedAt": null, "startedAt": null,
        "nextAction": "arrive"
      }
    ]
  }
}
```

`nextAction` is `arrive`, `start` or `complete`, following the booking's status. Phase 5 adds the stop list.

#### Trip actions

Each action is one call to `transitionBooking`. The history row carries the pool. A repeat of an action that already happened returns **200** with the current result (NFR-37). Any other starting state is `409 INVALID_TRANSITION` (FR-R8). Each returns `{ "pool": … }`, the trip after the change.

| Method | Route | Change | Sets | Reason |
|---|---|---|---|---|
| POST | `/driver/bookings/:id/arrive` | ACCEPTED → DRIVER_ARRIVED | `arrived_at` | `driver_arrived` |
| POST | `/driver/bookings/:id/start` | DRIVER_ARRIVED → STARTED | `started_at` | `started` |
| POST | `/driver/bookings/:id/complete` | STARTED → COMPLETED | `completed_at`, the `fares` row | `completed` |
| POST | `/driver/bookings/:id/cancel` | ACCEPTED or DRIVER_ARRIVED → REQUESTED | clears `pool_id`, `accepted_at`, `arrived_at` | `driver_cancel` |

**Complete.** The fare is worked out *before* the transaction, from the stored booking (pure maths, no map request). The transaction then transitions the booking, inserts the `fares` row and finishes the pool. The response adds the fare: `{ "pool": null, "fare": { … } }`. A repeat returns the stored fare.

**Driver cancel** (FR-D12). This is allowed until the trip starts; from `STARTED` it is `409 INVALID_TRANSITION`. The request is visible to drivers again straight away, including this one. A repeat is recognised when the booking has left this driver's pool and its latest history row is this driver's `driver_cancel`. It returns **200** with the current trip. The penalty for a cancel more than 3 minutes after acceptance (FR-D13) comes in phase 6.

### Driver: Tesla and availability

| Route | Change in this phase |
|---|---|
| `POST /driver/vehicle/offline` | `409 HAS_ACTIVE_BOOKINGS` while the Tesla has an active pool (FR-D3) |
| `PUT /driver/vehicle/location` | `409 HAS_ACTIVE_BOOKINGS` while the Tesla has an active pool. A driver with a passenger doesn't teleport. |

Both lock the Tesla row, check for an active pool in a separate statement, and then update. That way they wait for any accept already running and see the pool it created. A single `UPDATE … WHERE NOT EXISTS (…)` could miss it under READ COMMITTED.

### Passenger

#### `POST /bookings/:id/cancel`

This now also works from `ACCEPTED` and `DRIVER_ARRIVED`, until the trip starts (FR-P7). One transaction:

```sql
UPDATE bookings SET status = 'CANCELLED', cancelled_at = now()
WHERE id = $1 AND passenger_id = $2
  AND status IN ('REQUESTED', 'ACCEPTED', 'DRIVER_ARRIVED')
RETURNING …;
```

It goes through `transitionBooking` like every other change. The reason is decided by the database clock:

| Cancelled from | Reason |
|---|---|
| `REQUESTED` | `passenger_cancel` |
| `ACCEPTED`, `DRIVER_ARRIVED`, with `now() <= accepted_at + interval '3 minutes'` | `passenger_cancel` |
| `ACCEPTED`, `DRIVER_ARRIVED`, later | `late_cancel` (fined from phase 6) |

The pool is finished in the same transaction. From `STARTED` or `COMPLETED` it is `409 INVALID_TRANSITION`. Cancelling twice still returns 200.

#### The booking body

`/bookings/current`, `/bookings/:id`, `POST /bookings/:id/cancel` and `/me` return the same body. It gains:

| Field | Value |
|---|---|
| `driver` | `{ "name": "Jashim" }` once a driver has accepted, else `null` |
| `vehicle` | `{ "name": "Bullet" }` once a driver has accepted, else `null` |
| `acceptedAt`, `arrivedAt`, `startedAt`, `completedAt` | UTC times or `null` |
| `freeCancelUntil` | `accepted_at + 3 minutes`, calculated in SQL, or `null` |
| `notice` | `"driver_cancelled"` when the booking is `REQUESTED` again because its driver cancelled, else `null` |
| `fare` | The fare breakdown once `COMPLETED`, else `null` |

The fare breakdown has every figure needed to check it by hand (FR-F6, FR-P11):

```json
{
  "pickupOdometerKm": "0.000", "dropoffOdometerKm": "5.000",
  "actualKm": "5.000", "sharedKm": "0.000", "directKm": "5.000",
  "distanceMethod": "routed",
  "baseFare": "30.00", "perKmRate": "20.00", "sharedKmDiscount": "8.00",
  "seats": 1, "seatMultiplier": "1.00",
  "rideOption": "pool", "optionMultiplier": "1.00",
  "estimatedFare": "130.00", "computedFare": "130.00", "finalFare": "130.00"
}
```

The body describes the passenger's own booking only. It names the driver and the Tesla, never another passenger (FR-P8, NFR-9).

A completed or cancelled booking isn't "current", so `/bookings/current` returns `null` after it. The passenger's screen then reads `/bookings/:id` of the booking it was following, to show the result.

### Error codes added in this phase

| Status | Code | When |
|---|---|---|
| 409 | `ALREADY_CLAIMED` | Another driver accepted the request first |
| 409 | `SEATS_UNAVAILABLE` | The request needs more seats than the Tesla has |
| 409 | `HAS_ACTIVE_BOOKINGS` | The driver tried to go offline, or move, with a passenger |
| 422 | `NO_LONGER_MATCHES` | The driver isn't idle any more, or the pickup is out of range |
| 422 | `DRIVER_OFFLINE` | The driver accepted while offline |

Every 4xx is logged as a warning by the request logger, which covers conflicts and blocked actions (NFR-44).

## 4. Rules

### State machine (FR §6, FR-R8)

`domain/bookingStateMachine.ts` already holds the full FR §6 table. This phase uses every row except the no-show (`DRIVER_ARRIVED → CANCELLED` by the driver), which comes in phase 6. Every change goes through `transitionBooking`, which gains an optional `poolId` for the history row. Each service passes the states it starts from, so a skipped step (REQUESTED → STARTED, ACCEPTED → COMPLETED) never reaches the update.

### Finishing a pool (FR-R7)

Every transaction that can empty a pool (complete, driver cancel, passenger cancel) ends with:

```sql
UPDATE pools SET status = 'finished', finished_at = now()
WHERE id = $1 AND status = 'active'
  AND NOT EXISTS (
    SELECT 1 FROM bookings
    WHERE pool_id = $1 AND status IN ('ACCEPTED', 'DRIVER_ARRIVED', 'STARTED')
  );
```

### Lock order (FR-C7)

Driver actions lock the Tesla, then the booking, then touch the pool. A passenger cancel locks the booking, then touches the pool. No path takes them in the opposite order, so they can't deadlock.

### Final fare (FR-F4, FR-F5)

`domain/fare.ts` gains `finalFare`. It is pure and uses big.js, like `estimateFare`:

```
computed = (30 + 20 × actualKm − 8 × sharedKm) × seatMultiplier × optionMultiplier
estimate = (30 + 20 × directKm) × seatMultiplier × optionMultiplier
final    = min(computed, estimate)
```

Both are kept at full precision. The minimum is rounded half-up to 2 decimal places **once**, at the end. `computed_fare` is stored rounded the same way, for display.

| Case (FR §8) | Final fare |
|---|---|
| Pool, 1 seat: direct 5, actual 5.5, shared 3 | 116.00 |
| Same trip, 2 seats | 174.00 |
| Same trip, 2 seats, Same-gender | 182.70 |
| A single ride in this phase: actual = direct, shared 0 | the estimate |

### Nearby requests (FR-D5, FR-D6)

`domain/dispatch.ts` is pure (NFR-26). It holds `isNearby(tesla, pickup, radiusKm)`, which uses `haversineKm`, and `nextAction(status)`. Phase 5 grows it into the matching module.

## 9. Tests

The real map service is never called; distances use the fallback.

| Area | Cases |
|---|---|
| Final fare | The three FR §8 pooled examples: 116.00, 174.00, 182.70. A computed fare above the estimate is capped at it. Actual = direct with no sharing gives the estimate. The rounding happens once. |
| Nearby requests | Offline → none. Idle, inside the radius → listed with its distance. Outside the radius → not listed. More seats than the Tesla → not listed. Oldest first. Accepted and cancelled requests → not listed. A driver with a trip → none. A passenger → 403. |
| Accept | 200 with a new pool, `pool_id`, `accepted_at` and an `accepted` history row carrying the pool. The same driver twice → 200 and the same pool. A second driver → 409 `ALREADY_CLAIMED`. Offline → 422 `DRIVER_OFFLINE`. Busy → 422 `NO_LONGER_MATCHES`. A cancelled request → 409. Not a UUID, or not there → 404. |
| Trip | arrive → start → complete, each with its time and history row. Skipping a step → 409 `INVALID_TRANSITION`. A repeat of each step → 200. Another driver's booking → 404. The `fares` row checks by hand and `final = estimate`. The pool is finished, and the driver can go offline again. |
| Driver cancel | Back to `REQUESTED` with no pool, a `driver_cancel` history row with the old pool, the pool finished, and the request listed for drivers again. The passenger sees `notice`. A repeat → 200. After start → 409. |
| Passenger cancel | From `ACCEPTED` inside 3 minutes → `passenger_cancel`. With `accepted_at` moved back in SQL → `late_cancel`. From `STARTED` → 409. The pool is finished. |
| Passenger view | Shows the driver and Tesla after accept, and the fare after completion. Another passenger's booking → 404. |
| Availability | Offline or a location change during a trip → 409 `HAS_ACTIVE_BOOKINGS`. Both work again after completion. |
| Append-only | An UPDATE or a DELETE on `fares` is refused by the database. |
