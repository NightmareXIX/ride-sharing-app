# Phase 4 — Seats and concurrency: Low-Level Design

**Branch:** `feature/seat-capacity`
**Covers:** FR-R1 (in part), FR-R2, FR-R3, FR-R4, FR-D7 (free seats), FR-D9, FR-P10, FR-C1, FR-C2, FR-C3, FR-C5, FR-C6, FR-C7 · NFR-8, NFR-9, NFR-14, NFR-19, NFR-20, NFR-27, NFR-28, NFR-37, NFR-44

This phase lets a Tesla carry more than one booking, as long as it has free seats. Bullet has three. Each accept claims the seats it needs in the database, so two accepts racing for Bullet's last seat can't both win. This is the PRD's concurrency problem: Nusrat and Shirin both try to claim the one seat left. The phase also adds repeated stress tests for the guarantees built in earlier phases: only one driver claims a request, and a passenger holds one active booking.

---

## 1. Scope

**In**

- Each Tesla tracks the seats taken by the bookings it carries, and a version that changes whenever the Tesla changes.
- A driver with passengers can accept more requests while seats are free, including after a trip has started (FR-D9).
- An accept claims its seats with one conditional update. The database refuses anything above capacity (FR-C1).
- An accept checked against an out-of-date view of the Tesla is refused with `POOL_CHANGED` (FR-C3).
- Completing, cancelling or handing back a booking frees its seats in the same transaction.
- The request list for a Tesla with passengers shows only requests that fit the free seats.
- The driver sees how many seats are taken.
- Repeated concurrency tests against a real Postgres (NFR-27, NFR-28).

**Left for later phases**

| What | Phase |
|---|---|
| The matching rule (FR-L3), route stops and the odometer, shared km in the fare, `OUT_OF_STOP_ORDER`, the 3-requests-per-refresh route check | 5 |
| No-show (it frees seats with the helper added here), fines, driver penalties | 6 |
| Solo locking the Tesla and same-gender sharing (FR-R10) | 7 |

**A temporary joining rule.** In phase 3 a Tesla took one booking at a time. That made the seat limit unreachable: Bullet could never have "1 seat left". This phase drops that rule. Until phase 5 brings the matching rule (FR-L3), a request can join a Tesla's active pool when:

1. it fits the free seats, and
2. its pickup is within the search radius (default 2 km) of the Tesla, as it already had to be for an idle Tesla.

A Tesla with passengers can't move (phase 3), so the radius is measured from where the trip began. Phase 5 replaces rule 2 with FR-L3. Rule 1, the seat claim and the version check stay as they are.

**Fares are unchanged.** Every booking's fare is still worked out as a single ride: `actual = direct`, `shared = 0`, so the final fare is the estimate. Shared km needs the route stops of phase 5.

**The race, in this app.** Passengers don't pick a Tesla; a driver picks requests (FR-D8). So "Nusrat and Shirin both try to claim the last seat" means two accepts into Bullet running at the same moment: two taps, two browser tabs, or a retry landing next to the original. Exactly one wins. The other gets `409 SEATS_UNAVAILABLE`, and nothing about it changes (FR-R3).

## 2. Tables

One migration, `0008_add_vehicle_seats`, generated by drizzle-kit. The backfill at the end is hand-written.

### `vehicles` gains seats and a version

| Column | Type | Notes |
|---|---|---|
| `occupied_seats` | `integer` NOT NULL DEFAULT `0` | Seats held by the bookings the Tesla carries |
| `version` | `integer` NOT NULL DEFAULT `0` | Goes up by one on every change to the row |

- `CHECK vehicles_occupied_seats_range (occupied_seats BETWEEN 0 AND capacity)`. This is the database's last line of defence (FR-C1). A bug in the app can't overfill a Tesla or free more seats than it holds.
- **The invariant.** `occupied_seats` equals the total `seats` of the bookings in the Tesla's active pool whose status is `ACCEPTED`, `DRIVER_ARRIVED` or `STARTED`. Every transaction that moves a booking into or out of those states changes `occupied_seats` by that booking's seats. The tests check the invariant after every race.
- **The version.** Every write to a vehicle row sets `version = version + 1`. That covers seats, going online or offline, and moving. An accept remembers the version it checked, so any change in between is noticed (FR-C3).
- **Backfill.** The migration sets `occupied_seats` from the active bookings that already exist. That way a local database with a trip already running doesn't break the CHECK or the invariant.

The seat count and version live on the vehicle, not the pool (Core Entities §3). A Tesla has at most one active pool, so it is the one row to check and lock when accepting.

## 3. Routes

No new routes. Existing ones change as follows.

### `POST /driver/requests/:bookingId/accept`

The accept is split into a **snapshot** read outside any transaction and a short **commit**. The checks between them are pure. Phase 5 puts its route planning (map requests) in that gap, so no transaction waits on the map service (NFR-2, FR-C3).

**Snapshot and checks** (no locks):

1. Read the driver's Tesla: capacity, seats taken, version, online and location. Read the booking.
2. The booking is already in this Tesla's active pool → a repeat: **200** with the current trip (FR-C5, NFR-37).
3. Not there → `404`. Cancelled or completed → `409 INVALID_TRANSITION`. Taken by another Tesla → `409 ALREADY_CLAIMED`.
4. Offline → `422 DRIVER_OFFLINE`. Not enough free seats → `409 SEATS_UNAVAILABLE`. Pickup out of range → `422 NO_LONGER_MATCHES`.

**Commit** (one transaction, locking vehicle → booking → pool, FR-C7):

```sql
UPDATE vehicles
SET occupied_seats = occupied_seats + $seats, version = version + 1, updated_at = now()
WHERE id = $vehicle AND is_online AND version = $seenVersion
  AND occupied_seats + $seats <= capacity
RETURNING version;
```

This one statement both claims the seats and locks the Tesla row. If two accepts run it at once, Postgres makes the second wait for the first. The second then checks the `WHERE` again against the new row, and it no longer holds.

- **1 row:** use the Tesla's active pool, or insert one. Then `transitionBooking` REQUESTED → ACCEPTED sets `pool_id` and `accepted_at`, as in phase 3. If the booking is no longer `REQUESTED`, another driver claimed it first → `409 ALREADY_CLAIMED`. The whole transaction rolls back, including the seats and any new pool (FR-R3, FR-R4).
- **0 rows:** read the Tesla and the booking again, and say why:

| Found (in this order) | Response |
|---|---|
| The booking is in this Tesla's active pool: a double tap that won | **200** with the current trip |
| The booking isn't `REQUESTED` | `409 ALREADY_CLAIMED`, or `INVALID_TRANSITION` if it was cancelled |
| The Tesla is offline | `422 DRIVER_OFFLINE` |
| The seats no longer fit | `409 SEATS_UNAVAILABLE`: the last seat went to another accept |
| Anything else: the version moved | `409 POOL_CHANGED` "Your trip changed while accepting. Try again." |

The response is the driver's trip, as before.

### `GET /driver/requests`

| Driver's situation | Requests shown |
|---|---|
| Offline | None |
| Online, free seats | `REQUESTED` bookings with `seats ≤ capacity − occupied_seats` and a pickup within the radius |
| Online, Tesla full | None |

This replaces phase 3's "has an active pool → none". Oldest first, at most 20, as before.

### `GET /driver/pool` and the trip actions

The trip body gains the Tesla's seats, so the screen updates from the same response:

```json
{ "pool": { "id": "…", "createdAt": "…", "seats": { "capacity": 3, "taken": 2 }, "bookings": [ … ] } }
```

### Trip actions and cancels free seats

| Change | Seats |
|---|---|
| `complete`: STARTED → COMPLETED | freed |
| Driver `cancel`: ACCEPTED or DRIVER_ARRIVED → REQUESTED | freed |
| Passenger cancel from ACCEPTED or DRIVER_ARRIVED | freed |
| Passenger cancel from REQUESTED | none were held |

The seats are freed in the same transaction as the change, and a repeat frees nothing:

```sql
UPDATE vehicles
SET occupied_seats = occupied_seats - $seats, version = version + 1, updated_at = now()
WHERE id = $vehicle;
```

### `GET /driver/vehicle` and the availability routes

`vehicle` gains `occupiedSeats`. Going online or offline and moving now bump `version`. The phase 3 `HAS_ACTIVE_BOOKINGS` guard stays.

### `POST /bookings/:id/cancel` keeps the lock order

In phase 3 a passenger cancel locked only the booking. Now it also writes the vehicle, and it must lock the vehicle first, as every driver action does. Otherwise a cancel and a driver action could each hold the lock the other wants, and deadlock. The transaction now:

1. finds the booking's Tesla through its pool, without a lock
2. locks that Tesla, if there is one
3. locks the booking and moves it with `transitionBooking`, as in phase 3
4. if the booking left `ACCEPTED` or `DRIVER_ARRIVED`, frees its seats and finishes the pool if it is empty

The booking can change Tesla between steps 1 and 3: a driver hands it back and another driver accepts it. If that happens, the transaction rolls back and starts again, at most 3 times.

### Error codes added in this phase

| Status | Code | When |
|---|---|---|
| 409 | `POOL_CHANGED` | The Tesla changed between the accept's check and its commit. Try again. |

`SEATS_UNAVAILABLE` (phase 3) now also covers a lost race for the last seats. Every 4xx is logged as a warning (NFR-44).

## 4. Rules

### Where each guarantee lives (NFR-19, NFR-20)

No guarantee depends on the server's memory. Each holds with several copies of the API running.

| Guarantee | Enforced by |
|---|---|
| Seats never exceed capacity (FR-C1, FR-R2) | The conditional seat update, backed by `vehicles_occupied_seats_range` |
| Last-seat race: exactly one wins (FR-R3) | The same update. The row lock makes accepts on one Tesla take turns, and each checks the seats again. |
| One driver per request (FR-C2, FR-R4) | `transitionBooking`'s `UPDATE … WHERE status = 'REQUESTED'` after the booking row is locked |
| Out-of-date accepts refused (FR-C3) | `version = $seenVersion` in the seat update |
| A repeated accept isn't an error (FR-C5) | The snapshot check, and the 0-row check for a double tap |
| One active booking per passenger (FR-C6, FR-P10) | The partial unique index `bookings_one_active_per_passenger` (phase 2) |
| No deadlocks (FR-C7) | Every transaction locks vehicle → booking → pool |

### Seats (NFR-26)

`domain/seats.ts` is pure: `freeSeats(capacity, occupied)` and `fitsFreeSeats(capacity, occupied, seats)`. The request list, the accept checks and the error classification all use it.

### State machine

No change. `transitionBooking` now also returns the state the booking left, so callers know whether seats were held.

## 9. Tests

All against a real Postgres. The map service is never called (NFR-28). "Concurrently" means the calls are sent together with `Promise.all`. Each race test runs **25 rounds** from a clean set of rides, because timing bugs don't show up every time.

| Area | Cases |
|---|---|
| Seats (unit) | `freeSeats` and `fitsFreeSeats` at 0, at capacity, and one past it |
| Seat limit | Seats taken rise with each accept. Bookings join the same pool until Bullet is full. The next accept → 409 `SEATS_UNAVAILABLE`, and the list hides it. Accepting after a trip starts works (FR-D9). |
| Freeing seats | Complete, driver cancel and passenger cancel (from `ACCEPTED` and from `DRIVER_ARRIVED`) each free the seats. Freed requests show in the list again. A repeat frees nothing. |
| Database backstop | Raw SQL setting `occupied_seats` to 4 or −1 on Bullet is refused |
| Out-of-date accept | The snapshot is taken, the version is bumped in SQL, then the commit → 409 `POOL_CHANGED`, and nothing changes |
| Privacy | Two passengers in one Tesla each see only their own booking and fare |
| Last seat (×25) | Rafiq holds 2 seats. Accepts for Nusrat and Shirin (1 seat each) run concurrently → one 200, one 409 `SEATS_UNAVAILABLE`. Seats taken = 3. The loser is still `REQUESTED` with one history row. |
| Single claim (×25) | 3 drivers accept one request concurrently → one 200, two 409 `ALREADY_CLAIMED`. The losers have no pool and 0 seats. One `accepted` history row. |
| Double tap (×25) | The same driver accepts the same request twice concurrently → both 200 with the same pool, and the seats are counted once |
| Overfill (×25) | 5 one-seat requests are accepted concurrently into Bullet → exactly 3 succeed |
| Mixed (×25) | Accepts, passenger cancels and driver cancels run concurrently → no 500 (no deadlock), and the invariant holds |
| One active booking (×25) | 5 concurrent `POST /bookings` by one passenger. Identical bodies → one booking, and every response carries its id. Different bodies → one 201, and the rest 409 `ACTIVE_BOOKING_EXISTS`. |

After every race the tests check the invariant: `occupied_seats` equals the seats of the bookings in the active pool.
