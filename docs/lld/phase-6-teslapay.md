# Phase 6 — TeslaPay and fines: Low-Level Design

**Branch:** `feature/teslapay`
**Covers:** FR-W1–W8, FR-P7, FR-D11, FR-D13, FR-R9, FR-R11, FR-C7 · NFR-14, NFR-22, NFR-23, NFR-27, NFR-28, NFR-36, NFR-37, NFR-38, NFR-39, NFR-40, NFR-44

This phase makes money move. A passenger tops up their TeslaPay wallet with pretend money. Completing a TeslaPay ride takes the fare from the passenger and pays it to the driver; completing a Cash ride records the driver's earnings. A passenger who cancels late, or doesn't turn up, is fined 30 tk, even below zero. A driver who cancels late gets a penalty record. Every movement is written to an append-only ledger, and the wallet balance always matches it.

---

## 1. Scope

**In**

- The wallet ledger, `wallet_transactions`, append-only in the database (FR-W8, NFR-39).
- `GET /wallet`, `GET /wallet/transactions` (cursor pages), `POST /wallet/top-ups` (FR-W2).
- Settlement on completion: TeslaPay debit and driver credit, or a cash-earning entry (FR-W4, FR-W5).
- The 30 tk fine for a passenger cancel more than 3 minutes after acceptance (FR-P7, FR-W6).
- `POST /driver/bookings/:id/no-show`, allowed 5 minutes after arrival, with the 30 tk fine (FR-D11).
- `driver_penalties`, written by a driver cancel more than 3 minutes after acceptance (FR-D13).
- The seed tops up the story cast, so TeslaPay, a fine and the negative-balance block can be shown (FR-S3).

**Already in place**

- The balance checks when a ride is requested: `NEGATIVE_BALANCE` for Cash and TeslaPay alike (FR-W7), and `INSUFFICIENT_BALANCE` for TeslaPay below the estimate (FR-W3). Phase 2 built them against wallets that were all `0.00`. They don't change.
- The late-cancel reason, `late_cancel`, decided by the database clock (phase 3).
- The re-planning of a route when a booking leaves before pickup (phase 5). The no-show uses it.

**Left for later phases**

| What | Phase |
|---|---|
| Driver earnings totals (`GET /driver/earnings`), trip history | 8 |
| What a penalty leads to | Not decided (FR §13). Penalties are recorded, counted and shown to the driver. The README lists this as a known limitation. |

## 2. Tables

Two migrations, generated by drizzle-kit and reviewed by hand. The triggers are hand-written.

### `wallet_transactions` (Core Entities: WalletTransaction)

Migration `0011_create_wallet_transactions`. New enum `wallet_transaction_type`: `top_up`, `fare_payment`, `driver_credit`, `cash_earning`, `fine`.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | For a top-up, chosen by the client (§3) |
| `seq` | `bigint` GENERATED ALWAYS AS IDENTITY, UNIQUE | Insertion order. The history is sorted and paged by it, so two entries in the same microsecond still have a fixed order |
| `wallet_id` | `uuid` NOT NULL → `wallets.id` | |
| `booking_id` | `uuid` NULL → `bookings.id` | The ride the movement belongs to |
| `type` | `wallet_transaction_type` NOT NULL | |
| `amount` | `numeric(10,2)` NOT NULL | Signed: money in is positive, money out negative |
| `balance_after` | `numeric(10,2)` NOT NULL | The wallet's balance once this entry is applied |
| `created_at` | `timestamptz` NOT NULL DEFAULT `now()` | |

- `CHECK` on the sign: `top_up`, `driver_credit` and `cash_earning` are `> 0`; `fare_payment` and `fine` are `< 0`.
- `CHECK ((type = 'top_up') = (booking_id IS NULL))`: every other movement belongs to a ride.
- `UNIQUE (booking_id, type)` where `booking_id IS NOT NULL`: a ride is paid, credited, earned and fined at most once. It backs up the state machine against a double tap (NFR-37).
- Index `(wallet_id, seq)` for the history.
- **Append-only (NFR-39).** The trigger `wallet_transactions_append_only` runs the existing `reject_update_delete()` from `0005` `BEFORE UPDATE OR DELETE`. A mistake is fixed by adding a correcting entry.
- No backfill. Every wallet is still `0.00` with no entries behind it, so the ledger invariant (§4) already holds.

**Cash earnings don't touch the balance.** A Cash fare is paid in person, so the driver's wallet doesn't change (FR-W5). It is still a money movement, so it is recorded (FR-W8), with `balance_after` equal to the balance as it stands.

### `driver_penalties` (Core Entities: DriverPenalty)

Migration `0012_create_driver_penalties`.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | |
| `driver_id` | `uuid` NOT NULL → `users.id` | Indexed |
| `booking_id` | `uuid` NOT NULL → `bookings.id` | |
| `reason` | `text` NOT NULL | `late_driver_cancel` |
| `created_at` | `timestamptz` NOT NULL DEFAULT `now()` | |

The same trigger keeps it append-only (NFR-40). A booking can be accepted and dropped more than once, so there is no unique key: each late cancel is its own record.

## 3. Routes

### `GET /wallet`

Any signed-in user. `{ "wallet": { "balance": "447.98", "updatedAt": "…" } }`.

### `GET /wallet/transactions?cursor=…&limit=…`

Any signed-in user, their own wallet only (NFR-8). Newest first.

- `limit`: 1 to 50, default 20. Anything else is `400 VALIDATION_ERROR`.
- `cursor`: opaque, from the previous page's `nextCursor`. It encodes the last `seq` as base64url. A cursor that doesn't decode is `400 VALIDATION_ERROR`.
- One more row than `limit` is read; if it exists, `nextCursor` is set, else `null`.

```json
{
  "transactions": [
    { "id": "…", "type": "fine", "amount": "-30.00", "balanceAfter": "-10.00",
      "bookingId": "…", "reason": "late_cancel", "createdAt": "…" },
    { "id": "…", "type": "top_up", "amount": "20.00", "balanceAfter": "20.00",
      "bookingId": null, "reason": null, "createdAt": "…" }
  ],
  "nextCursor": null
}
```

`reason` says why a fine was charged, `late_cancel` or `no_show`, from the booking's history. It is `null` for every other type. The encoding and decoding of cursors live in `http/pagination.ts`, which phase 8's history lists reuse (NFR-36).

### `POST /wallet/top-ups`

Passengers only; a driver gets `403 WRONG_ROLE`. There is no payment gateway (FR-W2).

```json
{ "id": "6f1c…", "amount": "500.00" }
```

- `id`: a UUID the client makes when the top-up form opens. It becomes the ledger entry's id.
- `amount`: a string, up to two decimals, from `"1.00"` to `"10000.00"`. A number, a third decimal or anything out of range is `400 VALIDATION_ERROR`.

One transaction: lock the passenger's wallet, look up the id, then add the amount and insert the entry.

| Case | Response |
|---|---|
| New id | **201** `{ "transaction": …, "wallet": { "balance": … } }` |
| Same id, same wallet and amount: a second tap or a retry | **200** with the entry as first made (NFR-37) |
| Same id with another amount, or another user's id | `400 VALIDATION_ERROR` on `id`: "This top-up was already made with different details." |
| The balance would pass ৳ 100,000.00 | `422 BALANCE_LIMIT` "Your balance can't go above ৳ 100,000.00." |

Two taps racing each other wait on the wallet lock, so the second one finds the first one's entry. The primary key is the backstop.

### Completing a ride pays for it

`POST /driver/bookings/:id/complete` settles the ride in the transaction that records the fare, after the fare row (NFR-14, FR-C7):

| Payment | Entries |
|---|---|
| TeslaPay | The passenger's `fare_payment` of −final, then the driver's `driver_credit` of +final (FR-W4) |
| Cash | The driver's `cash_earning` of +final. No balance changes (FR-W5). |

For TeslaPay, both wallets are locked in one statement, in wallet-id order, so two settlements can't deadlock. The lock order stays **vehicle → booking → wallets** (FR-C7). The passenger's debit applies only while the balance covers it (§4). The response doesn't change: `{ "pool", "fare" }`. A repeated complete returns before any payment, and the unique key refuses a second one anyway.

### Late passenger cancel is fined

`POST /bookings/:id/cancel` from `ACCEPTED` or `DRIVER_ARRIVED` more than 3 minutes after acceptance already records `late_cancel`, by the database clock (FR-R9, NFR-38). The same transaction now posts a `fine` of −30.00 to the passenger's wallet, with the booking's id. It applies whatever the payment method, and it may take the balance below zero (FR-W6). The wallet is locked after the Tesla and the booking.

The booking body gains:

| Field | Value |
|---|---|
| `cancelFine` | `"30.00"` while cancelling now would be fined, else `null`. It is `now() > accepted_at + 3 minutes`, worked out in SQL at each read, so the passenger's screen warns from the right moment, give or take the 4-second poll. |
| `fine` | `{ "amount": "30.00", "reason": "late_cancel" }` once the booking was fined, else `null`. The reason is `late_cancel` or `no_show`. |

### `POST /driver/bookings/:id/no-show`

The driver cancels a passenger who didn't turn up (FR-D11). `DRIVER_ARRIVED → CANCELLED`, by the assigned driver. This is the one FR §6 row phase 3 left out.

Planned like a driver cancel (phase 5 §3). The route without the booking is measured **before** the transaction. The transaction then:

1. Locks the Tesla and checks its version. A moved version re-plans, up to 3 times, then `409 POOL_CHANGED`.
2. Locks the booking, which must be in this Tesla's trips; otherwise `404 NOT_FOUND`.
3. Checks the wait by the database clock: `now() >= arrived_at + interval '5 minutes'`. Too early → `422 NO_SHOW_TOO_EARLY` "You can mark a no-show 5 minutes after arriving." Nothing changes.
4. `transitionBooking` from `DRIVER_ARRIVED` to `CANCELLED`, reason `no_show`, setting `cancelled_at`. Like a passenger cancel, the booking keeps its `pool_id`.
5. Frees the seats, writes the re-planned route and finishes the trip if it is empty.
6. Posts the passenger's `fine` of −30.00.

| Case | Response |
|---|---|
| Done | **200** `{ "pool": … }` |
| Repeat: the booking is `CANCELLED` and its last history row is this driver's `no_show` | **200** with the trip as it is now, and no second fine (NFR-37) |
| `ACCEPTED`, `STARTED` or otherwise not arrived | `409 INVALID_TRANSITION` "Mark arrival first." / "The passenger is already aboard." |
| Another driver's booking | `404 NOT_FOUND` |
| A passenger calls it | `403 WRONG_ROLE` |

The arrived pickup is pinned as the next stop (phase 5), so no stop-order check is needed.

### Late driver cancel records a penalty

`POST /driver/bookings/:id/cancel` clears `accepted_at`, so the lateness is read first, on the locked booking, in the same transaction: `now() > accepted_at + interval '3 minutes'`. When it is late, a `driver_penalties` row with reason `late_driver_cancel` is inserted with the cancel (FR-D13). The passenger isn't fined, and the request goes back to other drivers as before. A second tap returns early, so it records nothing.

### What the driver sees

Each booking in `GET /driver/pool` gains:

| Field | Value |
|---|---|
| `noShowFrom` | `arrived_at + 5 minutes`, or `null` before arrival |
| `canNoShow` | `now() >= noShowFrom`, by the database clock |
| `penaltyFrom` | `accepted_at + 3 minutes` |
| `cancelRecordsPenalty` | `now() > penaltyFrom`, by the database clock |

The driver's Tesla body (`GET /driver/vehicle`, and the online, offline and location responses) gains `penaltyCount`, the number of the driver's penalty records.

### Error codes added in this phase

| Status | Code | When |
|---|---|---|
| 422 | `NO_SHOW_TOO_EARLY` | 5 minutes haven't passed since the driver arrived |
| 422 | `BALANCE_LIMIT` | A top-up would take the balance above ৳ 100,000.00 |

Every 4xx is logged as a warning (NFR-44).

## 4. Rules

### The wallet domain (NFR-26)

`domain/wallet.ts` is pure and uses big.js.

- `FINE_AMOUNT = '30.00'`, `MIN_TOP_UP = '1.00'`, `MAX_TOP_UP = '10000.00'`, `MAX_BALANCE = '100000.00'`.
- `signedAmount(type, amount)`: the amount with the sign its type needs.
- `affectsBalance(type)`: false for `cash_earning` only.
- `NO_SHOW_WAIT = '5 minutes'` sits in `domain/booking.ts` next to `FREE_CANCEL_WINDOW`, and is used inside SQL, like it.

`toTaka` in `domain/fare.ts` is exported, so every amount is formatted the same way.

### Posting an entry

`services/wallet.ts` is the only code that moves money. `postEntry(tx, { userId, type, amount, bookingId })` runs inside the caller's transaction:

1. For a type that affects the balance, one statement: `UPDATE wallets SET balance = balance + :amount, updated_at = now() WHERE user_id = :user RETURNING balance`. A `fare_payment` adds `AND balance + :amount >= 0`.
2. For `cash_earning`, the wallet is read `FOR UPDATE` and left as it is.
3. The entry is inserted with that balance as `balance_after`.

**A balance goes below zero only from a fine (FR-W6).** Top-ups and credits only add. A fare payment can't pass zero, by the condition in step 1. It never needs to: the balance covered the estimate when the ride was requested (FR-W3), the final fare is at most the estimate (FR-F5), and nothing takes money out between the two. The passenger has one active booking (FR-C6), and only that booking can fine them. If the condition ever fails, the complete rolls back with an error in the log, and nothing is paid.

**The ledger invariant**, checked after every race in the tests: for every wallet, the balance equals the sum of its entries' amounts, leaving out cash earnings. Walking the entries in `seq` order, each `balance_after` is the previous one plus its amount (or unchanged, for a cash earning).

### Where each guarantee lives

| Guarantee | Enforced by |
|---|---|
| The ledger is never edited (NFR-39) | `reject_update_delete()` on `wallet_transactions` |
| A ride is paid, credited or fined at most once | The state machine, then `UNIQUE (booking_id, type)` |
| A fare payment never goes below zero | `balance + amount >= 0` in the same `UPDATE` |
| Payment, credit and fare commit together (FR-C7, NFR-14) | One transaction, locking vehicle → booking → wallets |
| A double-tapped top-up adds once | The wallet lock, then the primary key on the client's id |
| Time windows use server time (FR-R9, NFR-38) | `now()` in SQL for the 3-minute and 5-minute checks |
| A negative balance blocks new requests (FR-W7) | Phase 2's check in `requestRide` |

## 7. Seed and the story

The seed tops up three passengers, each through one ledger entry with a fixed id, in the seed's transaction. The entry is inserted with `ON CONFLICT (id) DO NOTHING`, and the balance moves only when a row was inserted, so running the seed again changes nothing (NFR-31).

| Who | Top-up | Why |
|---|---|---|
| Nusrat | ৳ 500.00 | Pays the pooled ride by TeslaPay |
| Rafiq | ৳ 500.00 | Pays the pooled ride by TeslaPay |
| Shirin | ৳ 20.00 | Rides with Cash. A 30 tk fine takes her below zero, which shows the block. |
| Jashim | none | Earns from rides |

**Nusrat and Rafiq by TeslaPay, with no map key** (fares from phase 5 §7):

| | Nusrat | Rafiq | Jashim |
|---|---|---|---|
| Start | 500.00 | 500.00 | 0.00 |
| Nusrat dropped off: `fare_payment` / `driver_credit` 52.02 | 447.98 | | 52.02 |
| Rafiq dropped off: `fare_payment` / `driver_credit` 71.42 | | 428.58 | 123.44 |

**Shirin's late cancel.** Shirin requests a Cash ride and Jashim accepts. Four minutes later she cancels: `late_cancel`, a `fine` of −30.00, and her balance goes 20.00 → −10.00. Her next request, Cash or TeslaPay, is refused with `422 NEGATIVE_BALANCE`. She tops up ৳ 10.00 or more, and can request again.

**A no-show.** Jashim arrives at Rafiq's pickup. After 5 minutes the **No-show** button works; before that it gives `NO_SHOW_TOO_EARLY`. Rafiq is fined 30 tk, and his stops leave the route.

## 9. Tests

All against a real Postgres. The real map service is never called (NFR-28). Time windows are tested by moving `accepted_at` or `arrived_at` back in SQL, since only the database clock counts. Race tests run **25 rounds**, as in phase 4.

| Area | Cases |
|---|---|
| Wallet domain (unit) | Signs per type, `affectsBalance`, the top-up amount rules |
| Top-ups | 201 and the new balance. A repeat → 200 with the same entry. The same id with a new amount → 400. `"0.99"`, `"10000.01"`, `"5.001"`, a number → 400. A driver → 403. Past the cap → 422 `BALANCE_LIMIT`. |
| History | 25 entries read in pages of 10: newest first, no gaps, no repeats, `nextCursor` null at the end. A bad cursor or limit → 400. A user sees only their own entries. |
| Append-only | A raw `UPDATE` or `DELETE` on `wallet_transactions` or `driver_penalties` is refused by the database |
| Settlement | TeslaPay: the passenger's debit and the driver's credit, with the right `balance_after`. Cash: one `cash_earning`, no balance change. Nusrat and Rafiq by TeslaPay end at exactly 447.98, 428.58 and 123.44. A repeated complete doesn't pay twice. |
| Late cancel | Cancelling while waiting, or within 3 minutes of acceptance → no fine, and `cancelFine` is null. At 3 minutes 1 second → `cancelFine` is "30.00", and cancelling fines −30.00 on the booking for Cash and TeslaPay alike. From 0.00 the balance goes to −30.00, then a request → 422 `NEGATIVE_BALANCE`, and after a top-up the request works. The booking body shows the fine. |
| No-show | At 4 minutes 59 seconds → 422 `NO_SHOW_TOO_EARLY`, nothing changed. At 5 minutes → `CANCELLED` with reason `no_show`, a fine, the seats freed, the stops gone and the route re-planned, the trip finished if empty. From `ACCEPTED` → 409. Another driver's → 404. A passenger → 403. A repeat → 200 with one fine. |
| Driver penalty | A cancel within 3 minutes → no penalty. Later → one penalty, no fine for the passenger, and `penaltyCount` 1. A repeat adds nothing. |
| Seed | Balances 500.00, 500.00, 20.00 and 0.00, one top-up each, the same after a second run |
| Races (×25) | A double-tapped late cancel → one fine. A passenger cancel against a no-show → one wins, at most one fine. A double-tapped complete → one debit and one credit. Ten top-ups with one id → one entry. Ten different top-ups at once → the balance is their sum. Nusrat's and Rafiq's TeslaPay completes alongside top-ups → no deadlock and no 500.
