# Phase 2 — Requesting a ride: Low-Level Design

**Branch:** `feature/ride-request`
**Covers:** FR-P3, FR-P4 (estimate), FR-P5 (REQUESTED, CANCELLED), FR-P7 (free cancel before acceptance), FR-P9, FR-P10, FR-D3, FR-D4, FR-L1, FR-L2, FR-F1–FR-F3, FR-W3, FR-W7, FR-R8, FR-R11, FR-C4, FR-C6 · NFR-2, NFR-3, NFR-8, NFR-10, NFR-11, NFR-13, NFR-23, NFR-24, NFR-26, NFR-27, NFR-28, NFR-37, NFR-38, NFR-40, NFR-41, NFR-44

This phase lets a driver put their Tesla online at a location they set on the map, and lets a passenger price a trip and request a ride. A passenger can cancel the request while it waits. Road distances come from OpenRouteService, with a straight-line fallback when it can't answer. No driver sees or accepts a request yet.

---

## 1. Scope

**In**

- A driver sets their location on the map and goes online or offline.
- Road distance between two points: OpenRouteService, cached, with haversine × 1.3 as the fallback.
- A fare estimate for any trip, before booking.
- A passenger requests a ride with pickup, destination, seats, ride option and payment method.
- A passenger sees their current request, and cancels it for free while it waits for a driver.
- Every booking status change is written to an append-only history.
- A passenger holds at most one active booking. The database enforces it.

**Left for later phases**

| What | Phase |
|---|---|
| Blocking offline, and location changes, while the driver has passengers (`HAS_ACTIVE_BOOKINGS`). No booking can belong to a driver before accept exists. | 3 |
| Pools, `bookings.pool_id`, accept, arrive, start, complete, driver cancel, and their timestamps | 3 |
| Computed and final fare (FR-F4, FR-F5), the `fares` table | 3, 5 |
| `occupied_seats`, `version`, the seat CHECK, and the repeated concurrency stress tests | 4 |
| Top-ups, the wallet ledger, fines, and cancelling after acceptance | 6 |
| What Solo and Same-gender do to matching (FR-R10) | 7 |
| `GET /bookings` ride history | 8 |

Two rules are pulled forward from later phases on purpose:

- **One active booking per passenger (FR-C6, planned for phase 4).** Creating a request is only safe against a double tap (NFR-37) if the database refuses a second active booking, and `GET /bookings/current` assumes there is at most one. Phase 4 adds the repeated stress test.
- **Balance checks (FR-W3, FR-W7, planned for phase 6).** They are conditions for creating a request, so they belong with it. Every wallet is at `0.00` until phase 6 adds top-ups, so a TeslaPay request is refused with `INSUFFICIENT_BALANCE` until then. That is the correct answer, not a gap.

All three ride options and both payment methods are accepted and priced from this phase on. Phase 7 adds how Solo and Same-gender affect matching.

## 2. Tables

Three migrations, generated by drizzle-kit and reviewed by hand.

### `vehicles` gains availability (FR-D3, FR-D4)

| Column | Type | Notes |
|---|---|---|
| `is_online` | `boolean` NOT NULL DEFAULT `false` | |
| `current_lat` | `numeric(9,6)` NULL | Set by the driver on the map |
| `current_lng` | `numeric(9,6)` NULL | |

- `CHECK ((current_lat IS NULL) = (current_lng IS NULL))`: a location is both halves or neither.
- `CHECK (NOT is_online OR current_lat IS NOT NULL)`: a Tesla can't be online without a location. The service checks this first and answers `LOCATION_REQUIRED`. The constraint is the backstop.
- Six decimal places is about 11 cm, which is finer than anyone can click.

### `distance_cache` (Core Entities: DistanceCache)

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | |
| `origin_lat`, `origin_lng`, `dest_lat`, `dest_lng` | `numeric(9,6)` NOT NULL | |
| `distance_km` | `numeric(7,3)` NOT NULL | Metres precision |
| `method` | `distance_method` NOT NULL | Always `routed` today; see below |
| `created_at` | `timestamptz` NOT NULL DEFAULT `now()` | |

- `UNIQUE (origin_lat, origin_lng, dest_lat, dest_lng)`. The key has a direction, because A→B by road is not always B→A.
- **Only routed distances are cached.** A fallback costs nothing to recompute, and caching it would keep an approximate value even after the map service recovers.
- Writes use `ON CONFLICT DO NOTHING`, so two requests caching the same pair don't collide.

### `bookings` (Core Entities: Booking)

New enums:

| Enum | Values |
|---|---|
| `booking_status` | `REQUESTED`, `ACCEPTED`, `DRIVER_ARRIVED`, `STARTED`, `COMPLETED`, `CANCELLED` |
| `ride_option` | `pool`, `same_gender`, `solo` |
| `payment_method` | `cash`, `teslapay` |
| `distance_method` | `routed`, `fallback` |

`booking_status` holds all six states from FR §6 now, so later phases never need `ALTER TYPE`. The status values are uppercase to match the spec's state machine.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | |
| `passenger_id` | `uuid` NOT NULL → `users.id` | |
| `pickup_lat`, `pickup_lng` | `numeric(9,6)` NOT NULL | |
| `pickup_label` | `text` NOT NULL | e.g. "Banani Road 11" |
| `dest_lat`, `dest_lng` | `numeric(9,6)` NOT NULL | |
| `dest_label` | `text` NOT NULL | |
| `seats` | `integer` NOT NULL | `CHECK (seats BETWEEN 1 AND 6)` |
| `ride_option` | `ride_option` NOT NULL | |
| `payment_method` | `payment_method` NOT NULL | |
| `direct_km` | `numeric(7,3)` NOT NULL | `CHECK (direct_km > 0)`. Road distance at request time (FR-F3). |
| `distance_method` | `distance_method` NOT NULL | How `direct_km` was measured (NFR-13) |
| `estimated_fare` | `numeric(10,2)` NOT NULL | |
| `status` | `booking_status` NOT NULL DEFAULT `'REQUESTED'` | |
| `requested_at` | `timestamptz` NOT NULL DEFAULT `now()` | The database clock (NFR-38) |
| `cancelled_at` | `timestamptz` NULL | |

- `CHECK ((status = 'CANCELLED') = (cancelled_at IS NOT NULL))`
- **One active booking per passenger (FR-C6):** `CREATE UNIQUE INDEX bookings_one_active_per_passenger ON bookings (passenger_id) WHERE status NOT IN ('COMPLETED', 'CANCELLED')`.
- `direct_km`, `distance_method` and `estimated_fare` are written once and never recalculated (NFR-41).

### `booking_status_history` (FR-R11)

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | |
| `booking_id` | `uuid` NOT NULL → `bookings.id` | Indexed |
| `from_status` | `booking_status` NULL | NULL for the row that records creation |
| `to_status` | `booking_status` NOT NULL | |
| `actor_id` | `uuid` NOT NULL → `users.id` | Who made the change |
| `reason` | `text` NOT NULL | `requested`, `passenger_cancel` in this phase |
| `created_at` | `timestamptz` NOT NULL DEFAULT `now()` | |

- **Append-only, enforced by the database (NFR-40).** A trigger function `reject_update_delete()` raises an error `BEFORE UPDATE OR DELETE` on this table. Phase 6 attaches the same function to the wallet ledger (NFR-39). `TRUNCATE` doesn't fire row triggers, so tests can still reset the database.
- `pool_id` is added in phase 3, when pools exist.

## 3. Routes

All routes are under `/api/v1`. Bodies are validated with Zod. Invalid input returns `400 VALIDATION_ERROR` with `details: [{ path, message }]` (NFR-10).

### Shared input rules

A **point** is `{ "lat": 23.7937, "lng": 90.4066, "label": "Banani Road 11" }`.

| Field | Rule |
|---|---|
| `lat`, `lng` | Numbers inside the Dhaka service area: latitude 23.65 to 23.95, longitude 90.30 to 90.55. Anything outside gets 400. |
| `label` | Trimmed, 1–120 characters. Driver locations have no label. |
| pickup vs destination | At least 100 m apart in a straight line, otherwise 400 on `destination` |
| `seats` | A whole number from 1 to 6, and no more than the largest registered Tesla. A request no Tesla could carry gets 400 on `seats`. |
| `rideOption` | `pool`, `same_gender` or `solo` |
| `paymentMethod` | `cash` or `teslapay` |

Coordinates are rounded to 6 decimal places when parsed, so the cache key, the stored booking and the distance all use the same values.

**Assumption:** the app serves Dhaka only. The bounding box covers the city from Uttara to Old Dhaka. It keeps road distances sensible and saves map-service quota.

### Driver: Tesla and availability

All four use `requireAuth` and `requireRole('driver')`. The body of each is the driver's vehicle:

```json
{
  "vehicle": {
    "id": "…", "name": "Bullet", "capacity": 3, "isOnline": true,
    "location": { "lat": 23.7937, "lng": 90.4066 }
  }
}
```

`location` is `null` until the driver sets one.

| Method | Route | Behaviour |
|---|---|---|
| GET | `/driver/vehicle` | The Tesla as above |
| POST | `/driver/vehicle/online` | Sets `is_online`. Without a location it returns `422 LOCATION_REQUIRED`. Already online returns 200 with no change (NFR-37). |
| POST | `/driver/vehicle/offline` | Clears `is_online`. Already offline returns 200. Phase 3 adds the `HAS_ACTIVE_BOOKINGS` guard. |
| PUT | `/driver/vehicle/location` | `{ "lat", "lng" }` inside the service area. Allowed online or offline. |

### `POST /fare-estimates`

Passengers only. Nothing is booked. The only write is the distance cache.

```json
// request
{ "pickup": { "lat": 23.7937, "lng": 90.4066, "label": "Banani Road 11" },
  "destination": { "lat": 23.7781, "lng": 90.4050, "label": "Mohakhali" },
  "seats": 1, "rideOption": "pool" }

// 200
{ "directKm": "5.000", "distanceMethod": "routed",
  "baseFare": "30.00", "perKmRate": "20.00",
  "seatMultiplier": "1.00", "optionMultiplier": "1.00",
  "estimatedFare": "130.00" }
```

Every number in the response is a string, so the breakdown can be checked by hand with no float rounding (FR-F6).

### `POST /bookings`

Passengers only. The request is the estimate body plus `paymentMethod`.

The steps, in order:

1. Validate the body.
2. Read the passenger's wallet. A balance below zero returns `422 NEGATIVE_BALANCE` (FR-W7), for Cash and TeslaPay alike.
3. Measure the direct distance, then compute the estimate. Both happen **before** any transaction opens, so a slow map service never holds a database connection.
4. For TeslaPay, a balance below the estimate returns `422 INSUFFICIENT_BALANCE` (FR-W3).
5. In one transaction, insert the booking as `REQUESTED` and a history row `NULL → REQUESTED`, reason `requested`, with the passenger as actor.
6. If the insert breaks `bookings_one_active_per_passenger`, load the passenger's active booking:
   - If it is `REQUESTED` with the same pickup, destination, seats, ride option and payment method, the request is a repeat of the last tap. It returns **200** with that booking (NFR-37).
   - Otherwise it returns `409 ACTIVE_BOOKING_EXISTS` (FR-P10).

The unique index decides, not a lookup first, so two taps racing each other still create one booking.

Success is **201** with the booking:

```json
{
  "booking": {
    "id": "…", "status": "REQUESTED",
    "pickup": { "lat": 23.7937, "lng": 90.4066, "label": "Banani Road 11" },
    "destination": { "lat": 23.7781, "lng": 90.4050, "label": "Mohakhali" },
    "seats": 1, "rideOption": "pool", "paymentMethod": "cash",
    "directKm": "5.000", "distanceMethod": "routed", "estimatedFare": "130.00",
    "requestedAt": "2026-09-24T02:41:00.000Z", "cancelledAt": null
  }
}
```

A booking body only ever describes the passenger's own booking. It never names or prices another passenger (FR-P8, NFR-9). Phase 3 adds the driver and Tesla to it.

### `GET /bookings/current`

Passengers only. `{ "booking": … }` for the active booking, or `{ "booking": null }`. The app polls it every 4 seconds.

### `GET /bookings/:id`

Passengers only. The booking in any state, if it belongs to the passenger. Another passenger's booking, an id that doesn't exist and an id that isn't a UUID all return `404 NOT_FOUND` (FR-P9, NFR-8).

### `POST /bookings/:id/cancel`

Passengers only. In this phase, only `REQUESTED → CANCELLED` exists, and it is always free (FR-P7).

One transaction runs:

```sql
UPDATE bookings SET status = 'CANCELLED', cancelled_at = now()
WHERE id = $1 AND passenger_id = $2 AND status = 'REQUESTED'
RETURNING …;
```

and, if a row changed, inserts the history row `REQUESTED → CANCELLED`, reason `passenger_cancel` (FR-C4). If no row changed, the booking is looked up:

| Found | Response |
|---|---|
| Not the passenger's, or not there | `404 NOT_FOUND` |
| Already `CANCELLED` | **200** with the booking. Pressing Cancel twice is safe (NFR-37). |
| Any other state | `409 INVALID_TRANSITION` |

Cancelling after acceptance, with the 3-minute free window and the fine, comes in phases 3 and 6.

### `GET /me`

Gains `currentBooking`: the same booking body as `/bookings/current`, or `null`. It is always `null` for drivers. The phase 1 LLD left this field for this phase.

### Error codes added in this phase

| Status | Code | When |
|---|---|---|
| 409 | `ACTIVE_BOOKING_EXISTS` | The passenger already has an active booking with different details |
| 409 | `INVALID_TRANSITION` | The booking's current state doesn't allow the action |
| 422 | `NEGATIVE_BALANCE` | The wallet is below zero; top up first |
| 422 | `INSUFFICIENT_BALANCE` | TeslaPay chosen, and the balance is below the estimate |
| 422 | `LOCATION_REQUIRED` | A driver went online without setting a location. New in this LLD; not in the API Routes list. |

## 4. Rules

### Booking state machine (FR §6, FR-R8)

`domain/bookingStateMachine.ts` holds the whole FR §6 table as data: from state, to state, who may do it (passenger, or the assigned driver), and the reason. `assertTransition(from, to, actor)` throws `INVALID_TRANSITION` for anything else. This phase only uses `NULL → REQUESTED` and `REQUESTED → CANCELLED`, but the full table is written now so the rejected transitions can be tested (NFR-27).

Every change goes through one helper, `transitionBooking`. It runs the conditional `UPDATE … WHERE id = ? AND status = <expected>` and inserts the history row in the same transaction. Phases 3 to 6 reuse it for every other transition.

### Road distance (FR-L1, FR-L2, NFR-13)

`DistanceService.roadKm(from, to, log)` returns `{ km: "5.000", method: "routed" | "fallback" }`:

1. Look up the cache. A hit returns the stored routed distance.
2. Ask OpenRouteService: `POST {ORS_BASE_URL}/v2/directions/driving-car` with `{ "coordinates": [[lng, lat], [lng, lat]] }`. The key goes in the `Authorization` header, never in a URL or a log (NFR-11, NFR-43). The answer is `routes[0].summary.distance` in metres, kept to 3 decimal places of a km.
3. Cache the routed result.

It falls back to **haversine × 1.3**, rounded to 3 decimal places, **only** when the map service can't answer:

- no `ORS_API_KEY` is set
- a network error
- any non-2xx response, including 429 (quota used up) and ORS's "point not routable" errors
- a body without a distance
- no answer within **10 seconds**

A slow answer that arrives inside 10 seconds is used, even if it misses the 4-second target (NFR-2). Every fallback is logged as a warning with its reason, and so is any map request slower than 4 seconds (NFR-44). The service logs through the request's logger, so the warning carries the request id (NFR-42).

The service is built in `createApp` from `AppDeps.routing` (`apiKey`, `baseUrl`, `timeoutMs`). Tests pass their own values and never reach the real service (NFR-28).

### Fare estimate (FR-F1 to FR-F3)

`domain/fare.ts` is pure and uses **big.js** for exact decimal maths:

```
seatMultiplier   = 1 + 0.5 × (seats − 1)                     1.00, 1.50, 2.00 …
optionMultiplier = 1.00 pool · 1.05 same_gender · 1.15 solo
estimate         = (30 + 20 × directKm) × seatMultiplier × optionMultiplier
```

The product is kept at full precision and rounded half-up to 2 decimal places **once**, at the end (FR-F5). `directKm` is the stored 3-decimal value, so anyone can recompute the estimate from the booking by hand (FR-F6).

| Trip | Estimate |
|---|---|
| 5 km, Pool, 1 seat | 130.00 |
| 5 km, Pool, 2 seats | 195.00 |
| 5 km, Same-gender, 2 seats | 204.75 |
| 5 km, Solo, 1 seat | 149.50 |

## 5. Configuration

| Variable | Default | Purpose |
|---|---|---|
| `ORS_API_KEY` | unset | OpenRouteService key. Unset means every distance uses the fallback, which is how CI and an evaluator's machine run. |
| `ORS_BASE_URL` | `https://api.openrouteservice.org` | Lets tests point the client at a local stub |

The 10-second timeout is a constant passed through `AppDeps.routing`, so tests can shorten it. Compose passes `ORS_API_KEY: ${ORS_API_KEY:-}` to the API. The key never reaches the browser.

## 7. Seed (FR-S3)

The seed stays idempotent. It adds one step: if Bullet has no location, it is placed at Banani Road 11 (23.7937, 90.4066) and left offline. Jashim can go online straight away in the demo. Passengers pick their own points on the map, so no booking is seeded.

## 8. Frontend

| Screen | Contents |
|---|---|
| `/driver` | The Tesla card with an Online / Offline switch, a map to set the location, and the current location. Until phase 3: "Ride requests arrive in the next phase." |
| `/passenger`, no active booking | The request form: pickup and destination (map clicks or quick picks), seats, ride option with its multiplier, payment method with the TeslaPay balance, **Get estimate**, then **Request ride** |
| `/passenger`, active booking | "Looking for a driver…" with the route, seats, option, payment, estimate and request time, and a **Cancel request** button with a confirm step |

- **Map.** react-leaflet with OpenStreetMap tiles and the OSM credit shown (NFR-24). It is loaded only in the browser. Markers are circle markers, so there are no Leaflet icon files to bundle. The map opens on Dhaka.
- **Quick picks.** Banani Road 11, Mohakhali, Gulshan 1, Dhanmondi, Mirpur, Uttara, Farmgate and Bashundhara, each with coordinates, for people who'd rather not click the map.
- **Estimate.** Changing any input clears the shown estimate, so the price on screen always matches the form. A fallback distance shows "approximate: the map service is unavailable". After 3 seconds of waiting, the button reads "Calculating route…" (NFR-2).
- **Polling.** `/bookings/current` is fetched 4 seconds after the previous call finished, so slow calls never pile up (NFR-3).
- **Errors in plain words (NFR-22).** `INSUFFICIENT_BALANCE`: "Your TeslaPay balance is too low for this ride. Choose Cash." `NEGATIVE_BALANCE`: "Your balance is below zero. Top up before requesting a ride." `ACTIVE_BOOKING_EXISTS`: "You already have a ride in progress." A 400 on `seats` shows under the seat picker.
- Submit buttons are disabled while their request runs (NFR-37). Money is shown as `৳ 130.00`, and times in Dhaka time (NFR-23).

## 9. Tests

The real map service is never called. A local stub on `app.listen(0)` stands in for OpenRouteService and counts its hits.

| Area | Cases |
|---|---|
| Distance | A routed answer is used and cached: a second call makes no request. No key → fallback with no request. 500, 429 and a body without a distance → fallback. No answer within the (shortened) timeout → fallback. A slow answer inside the timeout → routed. Fallback results are not cached. A known haversine distance × 1.3 is rounded to 3 decimal places. |
| Fare | The four worked estimates above. A half-cent case rounds up. A case where rounding midway would change the result. |
| State machine | Every FR §6 row is allowed for its actor. REQUESTED → STARTED, COMPLETED → STARTED, STARTED → CANCELLED and a passenger starting their own ride are rejected. |
| Requests | 201 with a `NULL → REQUESTED` history row. 400 for seats 0 or 7, more seats than Bullet has, identical pickup and destination, a point outside Dhaka, and an unknown ride option. TeslaPay at `0.00` → 422 `INSUFFICIENT_BALANCE`. A negative balance → 422 `NEGATIVE_BALANCE`, for Cash too. The same request twice → 200 with the same booking. A different second request → 409. Ten identical requests at once, over several rounds → exactly one booking. |
| Reading | `/bookings/current` and `/me` return the active booking. Another passenger's booking → 404. A driver → 403. No session → 401. |
| Cancel | `REQUESTED → CANCELLED` with its history row. Cancelling twice → 200. Another passenger's booking → 404. After cancelling, a new request is allowed. |
| History | An UPDATE or a DELETE on `booking_status_history` is refused by the database. |
| Driver | Online without a location → 422. A location outside Dhaka → 400. Online and offline twice → 200 each time. A passenger on `/driver/*` → 403. |
| Seed | Bullet has its Banani location, and a second run changes nothing. |
