# Phase 5 — Pooling: Low-Level Design

**Branch:** `feature/tesla-pooling`
**Covers:** FR-R1, FR-D7, FR-D9, FR-D14 (stops), FR-L3, FR-L4, FR-L5, FR-F4, FR-F5, FR-F6, FR-P11, FR-C3, FR-C7 · NFR-2, NFR-3, NFR-13, NFR-19, NFR-22, NFR-26, NFR-27, NFR-28, NFR-37, NFR-41, NFR-44

This phase turns a Tesla carrying several bookings into a real pool. Each trip gets an ordered list of stops with an odometer reading at each one. A request can join a trip only if it fits the trip's remaining route, under the matching rule FR-L3. The driver follows the stops in order. Each passenger's fare is charged on the km they actually rode, less a discount for the km they shared. Nusrat and Rafiq's trip is the worked example, and the evaluator can check it by hand.

---

## 1. Scope

**In**

- Every trip has route stops: a pickup and a drop-off for each booking, in order, each with a planned odometer reading (FR-L5).
- An accept plans where the new stops go. For a Tesla with passengers, the request must pass the matching rule (FR-L3).
- The driver's request list shows only requests that fit the route. Each refresh route-checks at most 3 new requests (NFR-3).
- The driver must follow the stops in order (`OUT_OF_STOP_ORDER`).
- Picking up and dropping off record the odometer. Recorded readings never change (NFR-41).
- A passenger who leaves before pickup has their stops removed, and the rest of the route is re-planned.
- The final fare uses the pickup and drop-off readings and the shared km (FR-F4).
- The driver sees the stops in order with the next one marked.

**Left for later phases**

| What | Phase |
|---|---|
| No-show (it re-plans the route with the helper added here), fines, driver penalties | 6 |
| Solo locking the Tesla and same-gender sharing, FR-L3(f) | 7 |
| Trip history with its stops | 8 |

**This replaces phase 4's temporary joining rule.** Phase 4 let a request join a busy Tesla when its pickup was within 2 km of where the trip began. That rule is gone. A Tesla with passengers now takes only requests that pass FR-L3. An idle Tesla still sees requests within the search radius (FR-D6). The seat claim, the version check and the lock order from phase 4 stay as they are.

**Nusrat and Rafiq's trip (FR-L4).** With the phase 2 quick-pick coordinates, Nusrat (Banani → Mohakhali) and Rafiq (Banani → Gulshan 1) don't pool under FR-L3. Gulshan 1 branches off the way to Mohakhali. Whichever passenger is dropped second rides about 1.5 km extra, and the rule allows about 0.9 km. FR §13 left this open until routing was built and allowed adjusting the demo coordinates. The **Mohakhali pin moves to Wireless Gate (23.7812, 90.4090)**, where the Mohakhali–Gulshan 1 road begins. Going Banani → Mohakhali → Gulshan 1 is then close to Rafiq's direct route, and the two pool. §7 has the numbers. The matching rule is unchanged.

- **Backfill.** A local database may have a trip running from phase 4, with no stops. The migration lays out each active pool's bookings one after another, in accept order with `STARTED` ones first. Each gets a pickup and a drop-off `direct_km` further on, reached as its status says, with method `fallback`. The invariants in §4 then hold from the first start.

## 3. Routes

### The route model

A trip's odometer starts at **0 km where the Tesla stood when the trip began**. A Tesla with passengers can't move (phase 3), so that is the Tesla's current location. Each stop's planned km is the road distance along the route from there.

- **Reached stops always come first.** The driver follows the order, so the stops reached form a prefix of the route.
- **The next stop** is the unreached stop with the lowest sequence.
- **The anchor** is where the rest of the route is planned from:

| Situation | Anchor |
|---|---|
| A booking is `DRIVER_ARRIVED` | Its pickup, at its planned km. The driver is standing there, so it is pinned as the next stop and nothing is inserted before it. |
| Otherwise, some stop is reached | The last reached stop, at its reading |
| Otherwise | The trip's start, at 0 km |

Every change to the route bumps the Tesla's `version`, so an accept planned against an older route is refused (FR-C3). An accept, a cancel and a complete already bump it through the seat update. **Arrive and start now bump it too**, since they move the anchor.

### `GET /driver/requests`

| Driver's situation | Requests shown |
|---|---|
| Offline, or the Tesla is full | None |
| Online and idle | As in phase 4: `REQUESTED`, fits the seats, pickup within the search radius of the Tesla |
| Online with passengers | `REQUESTED`, fits the free seats, passes the quick check, and passes the matching rule against the current route |

For a Tesla with passengers, as NFR §2 describes:

1. **Quick check, no map.** The pickup is within the search radius, in a straight line, of the anchor or of a pending stop. It only narrows the list; the matching rule decides.
2. **Route check.** The survivors, oldest first, go through `bestInsertion` (§4) with road distances.
3. **At most 3 new checks per refresh (NFR-3).** A check is *new* if it needs a road distance that isn't in `distance_cache` and a map key is set, so it would make a map request. At most 3 of those run per refresh, in parallel. The rest are left out and checked on a later refresh. A request checked before against the same stops has all its distances cached, so it is free. With no key, nothing asks the map service, so every candidate is checked with the fallback. The limit is kept in the database, not the server's memory (NFR-19).

Each item gains `addedKm`: how much longer the Tesla's route gets if the driver accepts it. It is `null` for an idle Tesla. For a Tesla with passengers, `pickupDistanceKm` is measured from the anchor.

### `POST /driver/requests/:bookingId/accept`

Still the phase 4 snapshot → checks → commit. The route plan fills the gap phase 4 left for it, so no transaction waits on the map service (NFR-2, FR-C3):

1. **Snapshot**, no locks: the Tesla and its version, the booking, and the trip's route.
2. **Checks** as in phase 4: a repeat → 200; not found, cancelled, claimed, offline, no seats.
3. **Plan.** An idle Tesla: the pickup must be within the radius, and the route is start → pickup → drop-off. A Tesla with passengers: `bestInsertion`. No valid plan → `422 NO_LONGER_MATCHES` "This request no longer fits your route." One accept makes at most one map request.
4. **Commit**, one transaction: the seat update with `version = $seenVersion` (unchanged), the pool, `transitionBooking`, then the route. The unreached stops are deleted and the planned stops inserted, numbered after the last reached one. If the version moved, the phase 4 0-row analysis answers, ending in `409 POOL_CHANGED`.

### `GET /driver/pool` and the trip actions

The trip body gains the route:

```json
{
  "pool": {
    "id": "…", "createdAt": "…",
    "seats": { "capacity": 3, "taken": 2 },
    "odometerKm": "0.000",
    "stops": [
      { "id": "…", "bookingId": "…", "passenger": { "name": "Nusrat" }, "type": "pickup",
        "place": { "lat": 23.7937, "lng": 90.4066, "label": "Banani Road 11" },
        "sequence": 1, "plannedOdometerKm": "0.000", "actualOdometerKm": null,
        "reachedAt": null, "isNext": true }
    ],
    "bookings": [ { "…": "as before", "nextAction": "arrive", "canAct": true } ]
  }
}
```

- `stops` holds every stop of the trip, reached ones included, in sequence order.
- `odometerKm` is the anchor's km.
- `canAct` says whether the booking's `nextAction` can be taken now. `arrive` and `complete` need the booking's stop to be next. `start` always can, since an arrived pickup is pinned next.

### Stop order

`arrive` and `complete` check the order inside their transaction, after the Tesla is locked:

| Action | Allowed when |
|---|---|
| `arrive` | The next stop is this booking's pickup |
| `start` | The booking is `DRIVER_ARRIVED` (its pickup is pinned next) |
| `complete` | The next stop is this booking's drop-off |

Otherwise the response is `409 OUT_OF_STOP_ORDER`, and the message names the next stop in plain words, e.g. "Drop off Nusrat at Mohakhali first." A repeat of a step already taken returns 200 before the order is checked (NFR-37).

### Readings

| Action | Stop reached |
|---|---|
| `start` | The booking's pickup: `actual_odometer_km = planned_odometer_km`, `reached_at = now()` |
| `complete` | The booking's drop-off, the same way |

These are the two moments FR §6 records the odometer. `arrive` reaches nothing. If the passenger then doesn't come, their stop can still be removed.

### `complete` prices the ride from the route

The fare maths runs **before** the transaction, from a snapshot of the trip:

- `pickupOdometerKm`: the pickup's reading
- `dropoffOdometerKm`: the drop-off's planned km, which becomes its reading
- `actualKm = dropoff − pickup`
- `sharedKm`: from the other passengers' readings (§4)
- `routeDistanceMethod`: from the legs between the two stops

The transaction checks that the Tesla is still at the snapshot's version, then transitions the booking, reaches the stop, inserts the `fares` row, frees the seats and finishes the pool if it is empty. If the version moved, the work is done again from a new snapshot, up to 3 times, then `409 POOL_CHANGED`.

At completion every stop before the drop-off is reached, so every figure comes from recorded readings. A passenger still aboard counts as sharing up to this drop-off.

### Leaving before pickup re-plans the route

A driver cancel and a passenger cancel from `ACCEPTED` or `DRIVER_ARRIVED` delete the booking's stops. Neither can have been reached, since cancelling after `STARTED` isn't allowed. The remaining unreached stops get new planned km from the anchor, in the same order. Reached readings don't change (Core Entities §3).

The new planned km need road distances, so they are worked out **before** the transaction. The transaction checks the Tesla's version, and the work is redone on a change, as for `complete`, up to 3 times. The passenger cancel's phase 4 retry loop gains this check. The lock order is unchanged: vehicle → booking → stops (FR-C7). Phase 6's no-show uses the same path.

A cancel that removes the pinned arrived pickup moves the anchor back to the last reached stop. The km driven to that pickup belong to no one's ride, so they aren't charged to the passengers aboard.

### The passenger's booking

The fare breakdown gains `routeDistanceMethod`. Nothing else changes. A passenger sees their own shared km and discount, never who they shared with (FR-P8, NFR-9).

### Error codes added in this phase

| Status | Code | When |
|---|---|---|
| 409 | `OUT_OF_STOP_ORDER` | This passenger's stop isn't the next one |

`NO_LONGER_MATCHES` now also means "no longer fits the route". Every 4xx is logged as a warning (NFR-44).

## 4. Rules

### Route arithmetic (NFR-26)

`domain/route.ts` is pure and uses big.js, like `domain/fare.ts`. All km are strings with 3 decimal places.

- `plannedOdometers(anchor, points, leg)`: each point's km is the previous one's plus `leg(previous, point)`.
- `sharedKm(own, others)`: `own` is the passenger's `[pickupKm, dropoffKm]`, `others` the on-board intervals of the other bookings in the trip. The result is the length of `own` covered by the **union** of `others`, so two co-passengers aboard at once count once. The passenger's own seats don't count (FR-F1).

The planner's projection and the fare at completion use the same function, so a trip that goes as planned is priced as it was planned.

### The matching rule (FR-L3)

`domain/matching.ts` is pure. `bestInsertion(route, candidate, leg)` takes:

- the anchor
- the pending stops in order, with the first one pinned if it is an arrived pickup
- for each booking in the trip, its direct km and its pickup reading if it is aboard
- the candidate's pickup, drop-off and direct km
- `leg(a, b)`, the road km between two points

It tries every place for the new pickup and drop-off among the pending stops, with the pickup before the drop-off, and none before a pinned stop. Bullet's route has at most 6 pending stops, so that is at most 28 tries. A try is valid when:

| FR-L3 | Check |
|---|---|
| (a) pickup ahead on the route | The pickup goes on a leg of the remaining route, before an existing pending stop, and visiting it adds at most 1 km to that leg. A pickup after the route's end would branch off it. |
| (b) destination on the route after the pickup | A drop-off placed before an existing stop sits on the leg into that stop, adding at most 1 km to it, as the pickup must. A drop-off after the route's end extends the route instead; the newcomer's detour limit in (c) is what stops that end from branching. Without this check, a trip could "fit" a passenger by driving them somewhere and back before the next pickup: nobody's ride grows, but the route branches. |
| (c) small detours only | For every passenger whose ride gets longer, and for the newcomer: `detour = projected ride km − direct km ≤ 1 km`. |
| (d) nobody's fare above their estimate | For the same passengers: `detour ≤ 0.4 × projected shared km`. This is `computed ≤ estimate` with the seat and option multipliers cancelled out (FR-L3(d)). |
| (e) enough seats | The seat claim, unchanged from phase 4 |
| (f) solo, same-gender | Phase 7 |

A passenger whose ride doesn't get longer isn't checked, so earlier rounding can't block a later match. Of the valid tries, the one that makes the route shortest wins. On a tie, the one that keeps existing stops earlier wins: the latest pickup place, then the latest drop-off place. The result is a plan (the pending stops with their planned km, and `addedKm`) or a reason: `PICKUP_NOT_ON_ROUTE`, `DETOUR_TOO_LONG` or `FARE_ABOVE_ESTIMATE`. The reasons appear in logs and tests; the API says `NO_LONGER_MATCHES`.

`leg` of two identical points is 0 km, with no map request. Both story pickups are at Banani Road 11, where Bullet waits.

### Road distances for a route

A route check needs the distance between many pairs of points, and asking for them one by one could take nearly 30 map requests. So `DistanceService` gains `legKm(points, log, budget?)`:

1. Read every ordered pair of the points from `distance_cache` in one query.
2. If any are missing and a key is set, make **one** request to OpenRouteService's matrix endpoint, `POST {ORS_BASE_URL}/v2/matrix/driving-car` with `{ "locations": [[lng, lat], …], "metrics": ["distance"] }`. The key goes in the `Authorization` header as before. The routed answers are cached.
3. Pairs the map service can't answer use haversine × 1.3, with a warning, as in phase 2 (NFR-13). That covers no key, an error, 429, a timeout after 10 seconds, or a `null` entry. Slowness alone still isn't a reason.
4. If a request is needed but the caller's budget is spent, it returns `null` and the check waits for a later refresh.

It returns a `leg(a, b)` lookup and the method of each pair. `roadKm` stays as it is for estimates and bookings.

### Where each guarantee lives

| Guarantee | Enforced by |
|---|---|
| A route checked against an old version isn't applied (FR-C3) | `version = $seenVersion` in the seat update, and the version check in complete and the cancels |
| Readings never change (NFR-41) | `reject_reached_stop_change()` and the `actual = planned` CHECK |
| One pickup and one drop-off per booking | `UNIQUE (booking_id, type)` |
| One stop per place in the route | `UNIQUE (pool_id, sequence)` |
| Stop order | The next-stop check inside the transaction, after the Tesla lock |
| Fare never above the estimate (FR-P4) | The matching rule (d), then `min(computed, estimate)` and `CHECK (final_fare <= estimated_fare)` |

**The invariant**, checked after every race in the tests: every booking that is `ACCEPTED`, `DRIVER_ARRIVED` or `STARTED` has exactly one pickup and one drop-off stop in its pool, the pickup first. No other booking has stops in an active pool. Reached stops form a prefix. Phase 4's seat invariant still holds.

## 7. Seed and the story

No change to the seed. Passengers pick their own points. The Mohakhali quick pick moves to **(23.7812, 90.4090)**, and so does the test fixture.

**Nusrat and Rafiq, with no map key.** These are the fallback distances an evaluator's machine gets:

| Leg | Km |
|---|---|
| Banani Road 11 → Mohakhali | 1.835 |
| Banani Road 11 → Gulshan 1 | 2.287 |
| Mohakhali → Gulshan 1 | 0.970 |

1. Jashim goes online at Banani Road 11.
2. Nusrat requests Banani Road 11 → Mohakhali, 1 seat, Pool. Estimate `30 + 20 × 1.835 = ৳ 66.70`. Jashim accepts. Route: pickup Nusrat 0.000 → drop-off Nusrat 1.835.
3. Rafiq requests Banani Road 11 → Gulshan 1. Estimate `30 + 20 × 2.287 = ৳ 75.74`. His request shows with "Adds 0.970 km". Tries for his stops:

| Try | Result |
|---|---|
| Drop Nusrat, then Rafiq | Rafiq rides 2.805, detour 0.518, shares 1.835. 0.518 ≤ 1 ✓ and 0.518 ≤ 0.4 × 1.835 = 0.734 ✓. **Valid.** |
| Drop Rafiq, then Nusrat | Nusrat's ride grows to 3.257, detour 1.422 > 1 ✗ |

4. Jashim accepts. Route: pickup Nusrat 0.000 → pickup Rafiq 0.000 → drop-off Nusrat 1.835 → drop-off Rafiq 2.805.
5. Jashim arrives, starts, arrives, starts, completes Nusrat, completes Rafiq. Any other order is refused with `OUT_OF_STOP_ORDER`.

| | Nusrat | Rafiq |
|---|---|---|
| Odometer at pickup → drop-off | 0.000 → 1.835 | 0.000 → 2.805 |

## 9. Tests

All against a real Postgres. The real map service is never called (NFR-28): distances use the fallback, or a local stub of the directions and matrix endpoints that counts its hits. Race tests run **25 rounds**, as in phase 4.

| Area | Cases |
|---|---|
| Route (unit) | Planned km add up exactly. `sharedKm`: no overlap, partial overlap, nested, two co-passengers aboard at once counted once. The next stop and the anchor for each situation in §3. |
| Matching (unit) | Each reason: a pickup past the route's end, a detour over 1 km, a detour over 0.4 × shared km. An arrived pickup stays first. The shortest route wins, and ties go as §4 says. An unaffected passenger isn't checked. |
| Fare (unit) | FR §8's pooled example from stub legs: direct 5, rides 5.5, shares 3 → 116.00; 2 seats → 174.00; same-gender → 182.70 |
| Nusrat and Rafiq | The whole of §7 with the fallback: `addedKm` 0.970, the stop order, the readings, and final fares exactly 52.02 and 71.42, each matching its breakdown. The reverse order isn't chosen. |
| Off the route | Uttara → Mirpur while Bullet carries Nusrat: not listed, and accepting it → 422 `NO_LONGER_MATCHES`, nothing changed |
| Distances | One matrix request caches every pair. With part of the pairs cached, only the rest are requested. 500, 429, a `null` entry and a timeout → fallback for those pairs. A spent budget → `null` with no request. |
| 3 checks per refresh | 5 new requests on the route with the stub → the first refresh makes at most 3 map requests, the next picks up the rest, and a third makes none. With no key, all 5 are checked at once. |
| Stop order | Arrive at the second pickup first → 409 `OUT_OF_STOP_ORDER`. Complete Rafiq before Nusrat → 409. Repeats → 200. |
| Readings | Start and complete set `actual = planned` and `reached_at`. Raw SQL UPDATE or DELETE of a reached stop is refused by the database. |
| Re-planning | A passenger cancel and a driver cancel of a booking in the middle: its stops are gone, the later stops' planned km shrink, reached readings don't change, and the version goes up |
| Out-of-date accept | The snapshot is taken, an `arrive` lands, then the commit → 409 `POOL_CHANGED` |
| Privacy | Nusrat and Rafiq each see only their own booking and fare |
| Races (×25) | Phase 4's last seat, single claim, double tap and overfill, now with route stops. A mixed round of accepts, steps and cancels → no 500 and no deadlock. After each: the seat invariant and the route invariant from §4. |
